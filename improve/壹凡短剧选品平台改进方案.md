# 壹凡短剧选品平台改进方案

## 1. 总体定位

壹凡短剧选品平台应从“榜单采集与数据分析工具”升级为“短剧爆款选题与仿制创作中台”。

平台的核心差异化不应是直接替代 Runway、可灵、即梦、海螺、Sora、Veo 等通用视频生成工具，而是利用自身掌握的真实短剧榜单、评论、热度变化和分析报告，完成以下闭环：

```text
榜单采集 -> 爆款识别 -> 爆款拆解 -> 选题评分 -> 仿制方向 -> 剧本大纲 -> 人物/情节/场景 -> 分镜与制作包
```

也就是说，平台最重要的能力不是“凭空生成视频”，而是“基于真实市场反馈，自动发现可仿制爆款，并生成可落地的短剧创作方案”。

## 2. 市面方案观察

当前市面已有方案大致可分为几类：

| 类型 | 代表方案 | 强项 | 对本平台的启发 |
| --- | --- | --- | --- |
| AI 视频生成 | Runway、Luma、可灵、即梦、海螺、Sora、Veo | 文生视频、图生视频、镜头生成、角色和场景一致性 | 后续可作为分镜生成后的执行层，不宜一开始正面竞争 |
| AI 影视工作流 | LTX Studio、Google Flow/Veo | 脚本、分镜、镜头、场景、视频预演 | 平台应补齐“脚本到分镜”的结构化工作流 |
| 剪辑与模板化生产 | 剪映、CapCut | 脚本转视频、字幕、配音、模板剪辑 | 可学习其低门槛交互和制作包导出 |
| 配音与声音生成 | ElevenLabs 等 | 角色声音、旁白、配音 | 后续可接入分镜制作包，生成配音 prompt 或音频 |
| 通用写作/Agent | ChatGPT、Claude、Gemini 等 | 文本创作、结构化生成、推理 | 可作为剧本、人物、分镜生成的 LLM 底座 |

这些方案普遍缺少垂类短剧市场数据，不天然知道：

- 今天哪些短剧正在爆；
- 哪个题材开始增长；
- 哪些钩子和爽点更容易引发评论共鸣；
- 哪些剧目适合低成本仿制；
- 哪些爆款元素已经过热或有抄袭风险。

这正是壹凡短剧选品平台的机会点。

## 3. 当前平台基础

当前项目已经具备以下基础能力：

- dy/hg 榜单采集；
- 今日榜单与上一期榜单对比；
- 数据资产页；
- 分析看板；
- RAG 问答；
- dy/hg 分析报告；
- 评论、ASR、Markdown/TXT/JSON 等数据进入统一分析链路；
- OpenAI-compatible LLM 配置基础。

这些能力可以继续沉淀为“短剧创作智能体”的数据底座。

## 4. 核心改进模块

### 4.1 爆款拆解卡

对每个上榜短剧生成结构化拆解卡，字段建议包括：

- 剧名；
- 平台；
- 榜单排名；
- 热度、点赞、收藏、评论；
- 一句话卖点；
- 题材标签；
- 目标人群；
- 主角身份；
- 反派/阻力来源；
- 核心冲突；
- 前 3 集钩子；
- 爽点类型；
- 情绪曲线；
- 关键反转节点；
- 评论共鸣点；
- 可仿制元素；
- 不建议照抄的风险点；
- 制作难度评估。

爆款拆解卡应成为后续选题、仿制、剧本、分镜生成的最小业务单元。

### 4.2 选题评分系统

平台需要给每个剧目或候选选题生成综合评分，建议包含：

| 指标 | 含义 |
| --- | --- |
| 热度分 | 当前榜单热度、排名、点赞、收藏、评论等指标 |
| 增长分 | 与上一期相比的排名、热度、点赞、评论增长 |
| 评论共鸣分 | 评论区高频情绪、争议点、代入感 |
| 新鲜度分 | 题材是否过热，是否有新角度 |
| 可仿制分 | 是否能保留爽点但替换人设、背景、职业、关系 |
| 制作成本分 | 场景数量、人物数量、特效需求、服化道难度 |
| 平台适配分 | 是否适合 dy/hg 的内容形态和受众 |

最终输出：

```text
今日值得跟进选题 Top10
```

每个推荐选题都应给出推荐理由，而不是只给分数。

### 4.3 爆款仿制工坊

输入一个爆款短剧或一个趋势标签，输出 3-5 个差异化仿制方向。

每个仿制方向建议包含：

- 仿制方向标题；
- 借鉴的爆款元素；
- 必须差异化的元素；
- 新主角设定；
- 新核心冲突；
- 新故事背景；
- 前 3 集钩子；
- 主要爽点；
- 预期受众；
- 制作难度；
- 与原爆款的相似度风险；
- 推荐优先级。

仿制工坊的原则是：

```text
借鉴爽点，不复制表达；
借鉴结构，不复制剧情；
借鉴人群，不复制人设。
```

### 4.4 剧本工坊

不要一开始做“直接生成全集剧本”，容易失控。建议拆成可编辑工作流：

1. 选题 brief；
2. 世界观设定；
3. 人物小传；
4. 人物关系图；
5. 分集大纲；
6. 单集剧情 beats；
7. 正文剧本；
8. 台词润色；
9. 爽点增强；
10. 反转增强。

每一步都要支持：

- 重新生成；
- 手动编辑；
- 锁定当前版本；
- 基于当前版本继续生成；
- 导出 Markdown/JSON。

### 4.5 人物与关系库

人物生成不应只输出名字，而要输出可拍摄、可复用的角色卡：

- 角色名；
- 年龄段；
- 身份；
- 外在标签；
- 内在欲望；
- 核心秘密；
- 与主角关系；
- 与反派关系；
- 角色成长线；
- 高频台词风格；
- 造型参考 prompt；
- 声音参考 prompt。

人物关系库应沉淀常见短剧关系模板，例如：

- 隐婚/错认；
- 替嫁/真假千金；
- 重生复仇；
- 霸总追妻；
- 豪门继承；
- 玄学逆袭；
- 底层翻身；
- 师徒/养成；
- 双强博弈；
- 先婚后爱。

### 4.6 情节与场景库

情节库应沉淀可复用剧情积木：

- 开场羞辱；
- 身份误认；
- 关键证据出现；
- 反派陷害；
- 主角反击；
- 关系反转；
- 高能打脸；
- 情绪崩溃；
- 亲情/爱情确认；
- 结尾悬念。

场景库应沉淀低成本可拍场景：

- 办公室；
- 医院；
- 家中客厅；
- 酒店房间；
- 婚礼现场；
- 公司会议室；
- 豪门宴会；
- 学校走廊；
- 地下车库；
- 古风庭院；
- 修仙宗门大厅。

每个场景应标注：

- 制作成本；
- 适合题材；
- 可承载冲突；
- 常见镜头；
- 道具需求；
- AI 视频 prompt 模板。

### 4.7 分镜工坊

分镜工坊负责把剧本转成可执行镜头表。

每条分镜建议包含：

- 集数；
- 场次；
- 镜头序号；
- 场景；
- 出场人物；
- 镜头类型；
- 景别；
- 机位；
- 人物动作；
- 台词；
- 情绪目标；
- 道具；
- 光线/氛围；
- 时长建议；
- 视频生成 prompt；
- 配音 prompt；
- 字幕文本。

后续可对接外部视频生成工具，用分镜 prompt 批量生成预演素材。

## 7. 与现有模块的关系

### 7.1 今日榜单

今日榜单负责发现趋势：

```text
新上榜、排名上升、热度增长、点赞增长、评论增长
```

它应作为选题生成的入口。

### 7.2 分析看板

分析看板负责宏观统计：

```text
题材分布、热度趋势、评论情绪、高频卖点、剧目指标
```

它应为选题评分提供指标。

### 7.3 RAG 问答

RAG 负责引用证据：

```text
榜单文件、评论文件、分析报告、ASR 文本
```

生成选题、仿制方案、剧本时应尽量附带数据依据。

### 7.4 分析报告

分析报告负责深度拆解单个剧目。

后续应把 Markdown 报告升级为结构化 JSON：

```text
summary、selling_points、hook_points、plot_tags、character_roles、scene_patterns、imitation_notes
```

## 8. 生成质量控制

短剧仿制场景必须控制以下风险：

### 8.1 避免抄袭

生成结果应强制包含：

- 借鉴点；
- 差异点；
- 相似度风险；
- 修改建议。

### 8.2 避免空泛

每个选题都必须引用来源：

- 来源榜单；
- 来源剧目；
- 来源评论；
- 来源分析报告；
- 相关热度指标。

### 8.3 避免不可拍

每个方案都应评估：

- 场景数量；
- 主要人物数量；
- 特效需求；
- 服化道难度；
- 拍摄成本；
- 是否适合短剧节奏。

### 8.4 避免模型一次性失控

剧本生成应采用分步生成：

```text
选题 -> brief -> 人物 -> 大纲 -> 单集 beats -> 正文 -> 分镜
```

不要直接从榜单一步生成完整剧本。

## 10. 推荐优先级

最建议优先做：

1. 爆款拆解卡；
2. 选题评分；
3. 今日可跟进选题 Top10；
4. 仿制方向生成；
5. 人物设定与分集大纲；
6. 分镜 prompt；
7. 制作包导出；
8. 外部视频生成服务对接。

原因是：平台当前已有真实数据底座，应该先把数据转化成“创意决策能力”，再往视频生成和自动制作扩展。

## 11. 最终形态

最终平台应支持如下工作流：

```text
1. 查看今日榜单
2. 发现增长短剧
3. 一键生成爆款拆解卡
4. 生成可仿制选题
5. 选择一个方向生成剧本 brief
6. 生成角色、关系和分集大纲
7. 生成单集剧本
8. 生成场景与分镜
9. 导出制作包
10. 对接外部 AI 视频/配音/剪辑工具生成预演
```

这条路线能把壹凡短剧选品平台从数据看板升级成真正的短剧内容生产中台。

## 12. 创作数据库迁移至 PostgreSQL 的全面方案

> 方案日期：2026-09-14
>
> 迁移来源：`.runtime/creative/creative.db`
>
> 迁移目标：`AIWORKER_SYSTEM_DATABASE_URL` 指向的现有 PostgreSQL 数据库
>
> 方案状态：设计已确认

### 12.1 决策摘要

本次迁移采用“同库、全表、保留 ID、允许停机、一次性切换”的方式：

- 全部创作业务表迁入现有 PostgreSQL 的 `public` schema；
- 继续使用现有 `SystemDatabase` 引擎、连接池和 Alembic 版本链；
- 保留现有整数主键以及文本型业务 ID，不改为 UUID；
- 覆盖选题、拆解、项目、版本、自由创作、生成操作、审核、优化、交付、导出和历史迁移记录；
- 在维护窗口内停止 WebGUI 和后台任务，执行一致性备份、导入、验证和存储切换；
- 生产环境不采用双写；
- 原 SQLite 数据库只读封存 7 天，期间保留无损回退能力；
- 最终彻底移除运行时 SQLite、动态 DDL、`PRAGMA` 和文件路径依赖。

推荐实施路径是分阶段收敛：先建立 PostgreSQL schema 和仓储能力，再开发、演练迁移工具，最后执行维护窗口切换。禁止通过 SQL 文本翻译兼容层长期承载生产流量。

### 12.2 当前基线与问题

截至 2026-09-14，本机 `creative.db` 约 15 MB，SQLite `integrity_check` 结果为 `ok`。数据库中有 23 张现存业务表、约 1,826 行数据，主要数据量包括：

| 数据 | 数量 |
| --- | ---: |
| 选题 `creative_topics` | 637 |
| 拆解 `creative_breakdowns` | 42 |
| 创作项目 `creative_projects` | 18 |
| Brief `creative_blueprints` | 49 |
| 人物 `creative_characters` | 93 |
| 人物关系 `creative_relationships` | 117 |
| 分集大纲、Beats 和剧本 `creative_episodes` | 730 |
| 审核 `script_reviews` | 8 |
| 优化任务及草稿 | 9 |
| 选题阶段快照 `selection_stage_snapshots` | 65 |
| 幂等结果与生成操作 | 50 |

当前主要问题不是数据量，而是持久化边界和并发模型：

1. `creative/repository.py` 超过 7,000 行，混合了 schema 初始化、历史表升级、查询、业务状态机和回滚数据处理。
2. 仓储使用 SQLite 原生连接、`?` 参数和大量原始 SQL。
3. `delivery.py`、`production_exports.py` 和 `production_status.py` 仍在运行时创建或修改表。
4. WebGUI、审核 worker、优化 worker、拆解 worker 和剧本生成 worker 会自行根据 `creative.db` 路径创建仓储。
5. 创作库和系统 PostgreSQL 分开提交，项目、成员、任务、审批和审计之间存在半完成状态风险。
6. SQLite 文件级写锁不适合多 worker 并发生成、锁定版本和更新 Head。
7. 绝大多数 JSON 使用 `TEXT` 保存，数据库不能直接保证 JSON 有效性。
8. Unix 浮点时间戳、0/1 布尔值、动态补列和弱外键约束增加了数据治理成本。

### 12.3 目标与非目标

#### 目标

- PostgreSQL 成为创作数据的唯一运行时事实来源；
- schema 由 SQLAlchemy Core 元数据和 Alembic 唯一管理；
- SQLite 仅作为离线导入源和 7 天回退载体；
- 保持 API 返回结构、业务异常、版本语义、内容指纹和用户可见行为不变；
- 支持创作域与工作流域共享事务；
- 使用 PostgreSQL 行级锁、约束和 upsert 替代 SQLite 文件锁及手工竞争处理；
- 提供可重复演练、可审计、可验证、可回退的迁移流程；
- 保留全部现有 ID、版本链、资源 Head、工作流身份和历史记录。

#### 非目标

- 不在本次迁移中改造创作业务流程或前端交互；
- 不把整数主键统一替换为 UUID；
- 不顺带重写内容指纹、提示词版本或生产包协议；
- 不删除、合并或重编号历史创作版本；
- 不在生产环境长期保留 SQLite/PostgreSQL 双写；
- 不把导出文件、媒体文件和生产包二进制内容写入 PostgreSQL，数据库只保存路径、摘要和审计元数据。

### 12.4 目标架构

迁移后数据布局如下：

```text
AIWORKER_SYSTEM_DATABASE_URL
└── PostgreSQL / public
    ├── 身份与权限：users、roles、permissions、project_members
    ├── 工作流与审计：workflow_*、approval_records、audit_logs
    ├── 榜单：rank_snapshots、rank_entries
    └── 创作域
```

选择 `public` schema 的理由是现有创作表均已有 `creative_`、`script_` 等稳定前缀，可以避免新增 `search_path`、跨 schema Alembic 和测试环境配置。数据库连接、事务及健康检查继续由 `system_database` 负责，不再创建第二套 PostgreSQL 引擎。

建议代码边界：

```text
system_database/
├── database.py                  连接池、连接、事务和健康检查

creative/
├── database_schema.py           创作域 SQLAlchemy Core 表定义
```

### 12.5 全量表范围

所有现存表和代码中仍会动态创建的表都必须进入 SQLAlchemy 元数据与 Alembic，不能因当前为空而省略。

| 领域 | PostgreSQL 表 |
| --- | --- |
| 存储身份与迁移记录 | `creative_store_metadata`、`creative_mode_migrations`、`role_workflow_migrations` |
| 选题与拆解 | `creative_topics`、`creative_breakdowns`、`selection_stage_snapshots` |
| 项目与内容版本 | `creative_projects`、`creative_seeds`、`creative_blueprints`、`creative_characters`、`creative_relationships`、`creative_episodes` |
| 自由创作 | `creative_resource_heads`、`creative_generation_contexts` |
| 幂等、生成与删除 | `creative_operation_results`、`creative_generation_operations`、`creative_project_deletions` |
| 审核与优化 | `script_reviews`、`script_optimizations`、`script_optimization_drafts` |
| 交付与导出 | `creative_stage_exports`、`creative_deliveries`、`creative_production_exports`、`production_status` |

`creative_deliveries`、`creative_production_exports` 和 `production_status` 的运行时建表逻辑必须删除。`production_status` 即使在当前主库中尚未产生记录，也要作为正式表迁移，避免功能首次使用时再次生成 SQLite 文件。

此外新增 `creative_database_import_runs` 作为迁移控制表，记录源文件指纹、源 schema、应用版本、逐表统计、校验摘要、开始/结束时间和执行结果。该表不计入上述 24 张源业务表，但必须由 Alembic 管理。

### 12.6 数据类型与默认值映射

| SQLite 表达 | PostgreSQL 表达 | 迁移规则 |
| --- | --- | --- |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 显式导入原 ID，导入后重置 sequence |
| 普通 `INTEGER` ID | `BIGINT` | 不重编号，不改变对外表示 |
| 文本型业务 ID | `TEXT` | 保持原值，不强转 UUID |
| `REAL` Unix 时间戳 | `TIMESTAMPTZ` | 使用 UTC 转换，API 序列化兼容现状 |
| `captured_at` 文本时间 | `TIMESTAMPTZ` | 预检必须能解析，否则拒绝迁移 |
| `*_json`、`payload` JSON 文本 | `JSONB` | 导入前逐值解析，保留数组/对象/标量类型 |
| 0/1 标志位 | `BOOLEAN` | 只接受 0、1、`true`、`false` |
| `REAL` 评分和风险值 | `DOUBLE PRECISION` | 保持现有计算精度 |
| 状态字符串 | `TEXT` 加命名 `CHECK` | 状态集合以现有业务代码为准 |
| SQLite partial unique index | PostgreSQL partial unique index | 保持幂等与非空条件语义 |

JSONB 迁移前后需要使用规范化 JSON 计算内容校验值，但不能改写业务层现有内容指纹算法。数据库标准化造成的键顺序变化不得影响 API 返回或指纹校验。

为了保持接口契约，仓储出站层需要把 PostgreSQL `datetime` 转换为现有 API 约定的 Unix 时间戳或 ISO 字符串；不能把 SQLAlchemy `datetime` 对象直接泄漏给原本返回浮点时间戳的调用方。

### 12.7 主键、序列、唯一约束和外键

#### 主键与序列

- 保留所有整数 ID；
- 使用 `GENERATED BY DEFAULT`，允许迁移阶段显式插入原 ID；
- 每张 identity 表导入后执行 `setval`，下一值必须大于当前最大 ID；
- 对空表验证首次插入从约定起始值开始；
- 文本主键和复合主键保持现状。

#### 唯一约束

必须保留并命名以下关键语义：

- 选题来源唯一；
- 同一选题的拆解版本唯一；
- 同一项目的种子版本唯一；
- Brief 候选组版本唯一；
- 人物和关系批次键唯一；
- 同一项目、阶段、集数、版本唯一；
- 同一资源 Head 唯一；
- 项目创建请求、工作流任务和创建任务的部分唯一约束；
- 交付请求和生产包指纹唯一；
- 生成操作及幂等结果的操作 ID 唯一。

#### 外键策略

首次切换必须建立创作域内部已验证外键，例如项目到选题/拆解、资源到项目、种子父版本、优化到审核、优化草稿到优化任务。软删除归档表和需要保留历史证据的表不得配置会误删记录的级联删除。

`created_by`、`actor_id`、`workflow_task_id`、`submission_id` 等跨域引用先在预检报告中分类：

- 引用完整：建立或规划建立跨域外键；
- 合法历史缺口：保留索引和应用层校验，并在报告中记录原因；
- 非法孤儿：迁移前修复，禁止自动伪造用户、任务或提交记录。

为了保证 Alembic 在所有环境中确定性执行，首个创作基线 revision 只包含创作域内部外键。跨域外键在 7 天稳定期后，根据已确认的孤儿处理结果通过后续 Alembic revision 加固。

### 12.8 仓储和调用方改造

运行时仓储直接使用 SQLAlchemy Core，不使用 `PostgreSQLCompatConnection` 或其他 SQL 翻译层。

`CreativeRepository` 的迁移原则：

- 构造参数由 SQLite 文件路径改为 `SystemDatabase`；
- 支持接收已有 SQLAlchemy `Connection`，供跨仓储事务复用；
- 保持公开方法名称、返回字典、异常类型和异常文案；
- 内部按领域委托给小型仓储，避免继续扩大单文件；
- 使用 `RowMapping` 替代 `sqlite3.Row`；
- 使用 Core `select`、`insert`、`update`、`delete` 和显式 join；
- PostgreSQL 冲突处理使用 `sqlalchemy.dialects.postgresql.insert`；
- 删除所有 `CREATE TABLE`、`ALTER TABLE`、`PRAGMA`、`BEGIN IMMEDIATE` 和位置参数 SQL。

需要清理的生产调用点包括：

- `WebGUI.py` 中基于 `.runtime/creative/creative.db` 的共享仓储；
- `creative/api.py` 的默认 SQLite 仓储；
- 拆解、Phase 4、审核、项目审核和优化 worker；
- `workflow/transition_service.py` 的创作库路径推导；
- 生产包预检和导出的只读 SQLite 路径；
- 角色工作流迁移脚本和创作 CLI；
- 任务 payload 中的 `db_path`。

worker 只接收业务 ID 和操作 ID，从环境读取同一 PostgreSQL URL。不得把数据库 URL 或凭证写入任务 payload、日志、导出包或审计详情。

### 12.9 事务与并发模型

同库迁移的核心收益是把创作状态和工作流状态纳入同一事务。

以下操作应共享一个事务连接：

- 创建创作项目、建立项目成员和初始化工作流任务；
- 锁定阶段版本、生成提交快照和推进下一阶段任务；
- 删除或归档项目及同步工作流删除状态；
- 正式交付、工作流完成标记和审计登记；
- Writer Agent 创建、重做和回滚创作资源。

并发控制规则：

- 版本号分配、项目 revision、模式 revision 和 Head revision 使用行锁及乐观版本条件；
- 幂等操作依靠操作 ID、请求哈希和唯一约束，不使用“先查后写”作为唯一保护；
- 生成任务的占用、续租、完成和失败状态使用条件更新并检查影响行数；
- 同一项目需要跨多表串行化的操作使用事务级 PostgreSQL advisory lock，锁键由稳定 store ID 和项目 ID 派生；
- 最后一个负责人、资源锁定和任务领取等竞争读取使用 `SELECT ... FOR UPDATE`；
- 对死锁和序列化失败只重试已证明幂等的事务，并设置有限次数和抖动退避；
- 外部模型调用、文件生成和耗时计算不得占用数据库事务或行锁。

### 12.10 迁移工具设计

新增统一入口：

```powershell
uv run python scripts/migrate_creative_sqlite_to_postgres.py --source .runtime/creative/creative.db --check
uv run python scripts/migrate_creative_sqlite_to_postgres.py --source .runtime/creative/creative.db --apply
uv run python scripts/migrate_creative_sqlite_to_postgres.py --source .runtime/creative/creative.db --verify
```

#### `--check`

只读打开 SQLite，不连接目标库也能完成源数据检查：

- `PRAGMA integrity_check`；
- 表、列、索引和历史 schema 版本识别；
- 逐表行数、主键范围和源文件 SHA-256；
- JSON、时间戳、布尔值和状态值合法性；
- 唯一键重复检查；
- 项目、批次、父版本和 Head 引用检查；
- 工作流用户、任务和提交的引用清单；
- 文件路径只记录存在性和相对位置，不读取或迁移大文件内容。

`--check` 在未连接目标库时可以完成全部源数据检查；当 PostgreSQL 可用时，还必须只读检查目标表是否为空，并把用户、任务、提交和审计等跨域引用分类为完整、合法历史缺口或非法孤儿。

#### `--apply`

- 要求 PostgreSQL 可达且 Alembic 在指定 revision；
- 要求目标创作表为空；
- 在一个 PostgreSQL 事务中按依赖顺序导入；
- 保留全部主键和 store ID；
- 对 JSON、时间和布尔值执行确定性转换；
- 任一表失败则整体回滚；
- 不使用 `ON CONFLICT DO NOTHING` 隐藏冲突；
- 重置所有 identity sequence；
- 写入迁移运行记录、源指纹、应用版本、行数、哈希、开始/结束时间和结果。

目标表非空时默认拒绝运行。只有迁移记录中的源 SHA-256、schema 版本和完成状态完全相同，重复执行才能返回“已完成”；其他情况必须人工处理。

#### `--verify`

- 对比源表和目标表行数；
- 对类型标准化后的行按稳定主键排序并计算逐表哈希；
- 校验 sequence、唯一约束、外键和业务不变量；
- 输出机器可读 JSON 报告和适合人工审核的 Markdown 摘要；
- 任何差异均返回非零退出码。

### 12.11 实施阶段

#### 阶段 A：基线固定与契约测试

- 冻结当前 SQLite schema 快照和公开仓储接口清单；
- 为关键读写行为建立 SQLite/PostgreSQL 双后端契约测试；
- 覆盖排序、空值、异常、幂等和状态转换；
- 记录当前生产数据统计和业务不变量。

#### 阶段 B：PostgreSQL schema

- 创建 `creative/database_schema.py`；
- 把 24 张现存或动态表纳入 SQLAlchemy 元数据；
- 添加 Alembic 创作基线 revision；
- 在空 PostgreSQL 中验证 `upgrade head`；
- 验证从当前生产 revision 升级不会修改既有系统表数据。

#### 阶段 C：仓储分域迁移

建议顺序：

1. 选题、拆解和阶段快照；
2. 项目、种子和项目生命周期；
3. Brief、人物、关系和分集版本；
4. Head、上下文、幂等和生成操作；
5. 审核、优化和草稿；
6. 正式交付、阶段导出、生产包和生产状态；
7. Writer Agent 回滚与删除审计。

每一组先写 PostgreSQL 测试，再替换实现；门面接口在全部调用方迁完前保持稳定。

#### 阶段 D：跨域事务和 worker

- WebGUI 只创建一个 `SystemDatabase` 实例；
- 创作、身份、工作流和审计仓储共享该实例；
- 服务方法显式传递事务连接；
- worker 从环境连接 PostgreSQL，不再接收 `db_path`；
- 移除生产包和状态检查中的 SQLite 只读连接。

#### 阶段 E：迁移器与回退器

- 实现 `check/apply/verify`；
- 实现 PostgreSQL 到 legacy SQLite 的 7 天回退导出；
- 提供迁移报告、演练脚本和故障注入测试；
- 使用生产脱敏副本完成至少两次全流程演练。

#### 阶段 F：生产切换

- 执行维护窗口 runbook；
- 完成业务冒烟和负责人验收；
- 观察 7 天并保留回退能力；
- 稳定后删除运行时 SQLite 开关和反向回退入口。

#### 阶段 G：收尾加固

- 增加可确认安全的跨域外键；
- 删除未使用的 SQLite 依赖和测试辅助路径；
- 更新 README、开发命令、部署和备份文档；
- 将 PostgreSQL 创作库纳入日常备份、恢复演练和容量监控。

### 12.12 生产切换 Runbook

切换前至少提前一个工作日完成迁移预检和演练。正式窗口按以下顺序操作：

1. 宣布维护开始，阻止新登录写操作和新任务创建。
2. 停止 WebGUI、worker、定时任务及其他可能访问 `creative.db` 的进程。
3. 确认创作相关任务不存在 `queued`、`running`、`cancelling` 等未决状态；需要续跑的任务记录恢复信息。
4. 使用 SQLite Backup API 创建一致性备份，连同可能存在的 WAL 状态一并固化；记录 SHA-256。
5. 对现有 PostgreSQL 执行逻辑备份，并验证备份文件可读取。
6. 运行创作迁移 `--check`，保存 JSON 和 Markdown 报告。
7. 执行 `alembic upgrade head`。
8. 执行 `--apply`，确认事务提交和 sequence 重置成功。
9. 执行 `--verify`，要求结构、数量、内容和业务不变量全部通过。
10. 将过渡版本的创作存储开关切换为 PostgreSQL。
11. 启动 WebGUI，再启动 worker；检查数据库连接池、Alembic head 和创作存储健康状态。
12. 执行项目列表、版本读取、新建草稿、锁定、审核、优化、交付和生产包导出冒烟测试。
13. 由业务负责人抽查至少一个原创项目、一个仿写项目和一个包含完整剧本的项目。
14. 解除维护模式，记录实际停机时间和切换版本。
15. 将原 `creative.db` 改名为带日期和 SHA-256 前缀的只读归档，不允许应用继续访问。

任何强制验证项失败都必须停止切换，不得以人工口头确认跳过。

### 12.13 回退方案

#### 服务恢复前回退

如果导入、验证或冒烟测试在解除维护前失败：

- 停止新版本进程；
- 回滚应用存储开关或应用版本；
- 恢复原 SQLite 文件路径和权限；
- 如 Alembic 只新增了空创作表，可保留并等待问题修复；不得在未验证 downgrade 的情况下直接降级生产 schema；
- 启动旧版本并验证项目读取和任务状态。

#### 服务恢复后 7 天内回退

为避免丢失 PostgreSQL 切换后的新增数据，不能直接启用旧 SQLite：

1. 重新进入维护模式并停止全部写入；
2. 对 PostgreSQL 创作表和系统表执行一致性备份；
3. 使用 `creative/sqlite_rollback.py` 从 PostgreSQL 生成新的 legacy SQLite 文件；
4. 保留所有 ID、store ID、JSON、时间和版本关系；
5. 对新 SQLite 执行完整性、行数、哈希和业务不变量校验；
6. 使用仍支持 SQLite 的过渡应用版本完成冒烟；
7. 验证通过后才允许回切。

回退导出必须生成新文件，禁止覆盖原始封存副本。满 7 天并经负责人确认后，PostgreSQL 成为不可逆的唯一事实来源，运行时 SQLite 分支及反向导出入口从代码中删除；历史备份继续按保留策略归档。

### 12.14 测试策略

#### 仓储契约测试

过渡期使用同一组场景验证 SQLite 和 PostgreSQL：

- 返回字段、类型和排序一致；
- `None`、空字符串、空数组和空对象语义一致；
- 业务异常类型和文案一致；
- 状态转换及审计 payload 一致；
- 内容指纹和请求哈希一致。

#### PostgreSQL 集成测试

- 使用 `AIWORKER_TEST_SYSTEM_DATABASE_URL` 指向隔离测试库；
- 测试启动前拒绝数据库名 `aiworker_system` 等生产名称；
- 每个测试通过事务回滚或隔离 schema 清理数据；
- 覆盖 JSONB、`TIMESTAMPTZ`、identity sequence、部分索引和外键；
- CI 使用现有 PostgreSQL service，并增加创作迁移独立作业。

#### 并发测试

- 相同创建请求只生成一个项目；
- 相同版本竞争只允许一个成功；
- 旧 Head revision 不能覆盖新 Head；
- 同一生成操作只允许一个 owner；
- 续租、失效回收和完成之间不存在重复结果；
- 最后负责人保护、审核确认和交付去重在并发下成立；
- 跨创作/工作流事务发生异常时全部回滚。

#### 迁移测试

- 当前 schema、各历史 schema 和空库；
- 非法 JSON、非法时间、非法布尔和未知状态；
- 重复唯一键、断裂父版本和孤儿 Head；
- 目标非空、导入中断和重复运行；
- sequence 重置及迁移后新增数据；
- PostgreSQL 到 SQLite 无损回退。

#### 端到端测试

至少完整覆盖：

```text
榜单选题
→ 采纳与拆解
→ 创建原创/仿写项目
→ Brief
→ 人物与关系
→ 全剧大纲
→ Beats
→ 场次剧本
→ 锁定与修订
→ 审核和优化
→ 正式交付/生产包导出
```

### 12.15 验证标准

迁移验证分为四层：

1. **结构验证**：表、列、类型、默认值、约束、索引和 Alembic revision 完整。
2. **数量验证**：逐表行数、最小/最大 ID、空表和 sequence 状态一致。
3. **内容验证**：SQLite 与 PostgreSQL 数据经类型标准化后逐行、逐表哈希一致。
4. **业务验证**：项目版本链、当前资源、Head、生成操作、审核优化、交付、工作流身份和文件引用均可解析。

必须明确验证以下业务不变量：

- `creative_store_metadata.store_id` 未变化；
- 每个 workflow project/topic ID 仍可解码到原本地 ID；
- 所有 active 项目的种子和当前阶段引用可读取；
- `parent_version_id` 不形成断链或环；
- Head 指向同项目、同阶段、同集数的有效资源；
- 已锁定资源的锁定时间和内容指纹不变；
- 已完成生成操作仍能恢复其结果；
- 审核、优化和草稿引用的项目及分集资源可读取；
- 正式交付和生产包记录对应的文件路径、大小及 SHA-256 可验证；
- 软删除项目及删除审计不会因外键或清理逻辑丢失。

### 12.16 性能、可观测性与运维

上线前对以下高频查询执行 `EXPLAIN (ANALYZE, BUFFERS)`：

- 项目列表及按成员可见性过滤；
- 项目五阶段当前版本读取；
- 每集 Beats/剧本版本列表；
- 当前 Head 和 generation context 查询；
- 待执行或可恢复的生成操作；
- 审核、优化和交付历史列表。

索引必须来自真实查询条件，不机械复制 SQLite 索引。优先考虑项目、状态、阶段、集数、更新时间和软删除组合索引。

运行监控至少包含：

- PostgreSQL 和 Alembic head 健康状态；
- 创作存储后端标识；
- 连接池占用、等待和超时；
- 慢查询、锁等待和死锁；
- 事务回滚、唯一冲突和重试次数；
- 生成操作租约过期与恢复次数；
- 迁移及回退报告归档位置。

备份策略需要覆盖同一 PostgreSQL 中的系统域和创作域，保证时间点一致性。恢复演练不能只恢复创作表而遗漏用户、成员、任务、审批和审计。

### 12.17 安全要求

- 数据库 URL 只从环境读取；
- 日志和健康接口仅显示脱敏 URL；
- 迁移报告不得包含密钥、Cookie、模型凭证或完整敏感内容；
- 迁移工具使用专用运维权限，应用账号不授予 Alembic DDL 权限；
- 应用账号遵循最小的表级 DML 和 sequence 权限；
- SQLite 源与备份继承受限文件权限，不上传到仓库；
- 迁移 CLI 明确拒绝不安全的目标数据库名称和未处于维护模式的执行；
- 删除、回退和覆盖文件必须使用经过解析并限制在工作目录内的绝对路径。

### 12.18 主要风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| SQLite 与 PostgreSQL 查询语义差异 | 排序、空值、大小写行为变化 | 契约测试、显式排序和大小写条件 |
| JSON 文本转 JSONB | 指纹或输出顺序变化 | 规范化校验，业务指纹算法保持不变 |
| 时间戳转换错误 | 排序、租约和审计时间异常 | 全部按 UTC 转换并做边界测试 |
| sequence 未重置 | 切换后首次写入主键冲突 | 逐表 `setval` 和新增行验证 |
| 历史孤儿引用 | 外键创建或导入失败 | 预检分类、先内部外键、禁止伪造数据 |
| worker 仍访问旧文件 | 产生分叉数据 | 清理 `db_path`，启动时拒绝 SQLite 后端 |
| 长事务或锁顺序不一致 | 死锁和请求阻塞 | 缩短事务、固定锁顺序、并发测试和监控 |
| 导出文件与数据库记录不一致 | 正式交付不可追溯 | 校验路径、大小、哈希，文件仍单独备份 |
| 回退导致切换后数据丢失 | 业务成果丢失 | PostgreSQL → SQLite 反向导出后再回切 |
| 单文件仓储改动过大 | 回归面不可控 | 按领域拆分、兼容门面和阶段性测试 |

### 12.20 工期与人员建议

### 12.21 完成标准

只有同时满足以下条件，才能宣布迁移完成：

- 24 张现存或动态业务表及迁移控制表全部由 Alembic 管理；
- 所有源数据完成无损导入，数量和标准化内容哈希一致；
- 原整数 ID、store ID、版本链、Head 和工作流身份保持不变；
- PostgreSQL sequence、约束、索引和业务不变量验证通过；
- 创作全链路、并发场景和无损回退演练通过；
- WebGUI、worker、审核、优化、交付和导出均只访问 PostgreSQL；
- 运行时代码不再引用 `creative.db`、`sqlite3`、`PRAGMA` 或动态 DDL；
- 7 天观察期无阻断性故障，业务负责人完成验收；
- SQLite 运行分支已删除，备份进入只读归档；
- 运维、恢复、监控和安全文档同步生效。

最终目标不是简单“把 SQLite 表复制到 PostgreSQL”，而是把创作域正式纳入统一、可迁移、可审计、支持并发且能与工作流保持事务一致的数据基础设施。
