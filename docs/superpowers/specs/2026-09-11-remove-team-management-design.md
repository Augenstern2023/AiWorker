# 移除团队管理与多系统管理员契约设计

## 背景

当前系统同时存在两套账号与角色管理入口：

- `/review/users`、`/review/roles` 提供受限的“团队账号”和“角色授权”；
- `/admin/users`、`/admin/roles`、`/admin/navigation` 提供系统级用户、角色和页面管理。

团队入口与系统入口共享模板和前端脚本，但切换不同 API。该设计增加了理解和维护成本，并且当前团队接口仍能读取全量账号资料、团队角色缺少页面授权等，实际隔离边界与页面文案不一致。因此移除整套团队管理能力，只保留系统管理入口。

系统管理员身份继续由 `system_admin` 角色代码判断。`"*"` 只是通配业务权限，单独拥有 `"*"` 的账户不自动成为系统管理员。

## 目标

1. 物理删除团队管理页面、API、导航、权限目录和前端兼容分支。
2. 清除 PostgreSQL 中遗留的团队页面授权、导航项和专用权限数据。
3. 让所有团队页面与团队 API 旧地址直接返回 404，不保留重定向或兼容端点。
4. 明确并验证系统管理员角色允许分配给多个账户。
5. 保留“系统必须至少存在一个启用且绑定 `system_admin` 角色的账户”的安全保护。

## 非目标

- 不删除系统级用户管理、角色管理、页面授权和导航配置。
- 不改变普通业务角色、项目成员或任务分配模型。
- 不把仅拥有 `"*"` 权限的自定义角色视为系统管理员。
- 不改变首次初始化只能执行一次的 `/setup` 规则。
- 不迁移或删除现有普通用户、角色、项目成员和任务数据。

## 方案

采用“物理删除 + 数据清理迁移”。不保留返回 404 的占位处理器；移除路由注册后由 FastAPI 自然返回 404。

### 路由与服务

- 删除 `identity/team_api.py`。
- 从 `WebGUI.py` 删除 `build_team_management_router` 的导入和挂载。
- 从页面路由和模板映射删除 `/review/users`、`/review/roles`。
- 从页面 API 绑定目录删除全部 `/api/team/*` 路由。
- `/admin/users`、`/admin/roles`、`/admin/navigation` 及其 API 保持不变。

### 前端

`templates/admin/users.html`、`templates/admin/roles.html` 以及对应 JavaScript 继续服务系统管理页面，但删除所有 `team_mode`/`teamMode` 分支：

- 用户页面固定使用 `/api/admin/users`、`/api/admin/roles` 和部门接口；
- 角色页面固定使用 `/api/admin/roles`、`/api/admin/permissions` 和角色页面授权接口；
- 删除团队版标题、表格字段、按钮和受限 API 选择逻辑；
- 保留系统管理员现有筛选、导出、在线状态、部门和页面授权能力。

### 权限与导航目录

从代码目录中删除团队导航父项及两个子项，并删除仅由团队管理使用的七个权限代码：

- `page.team_management`
- `identity.user.read`
- `identity.user.create`
- `identity.user.manage_created`
- `identity.role.read`
- `identity.role.create`
- `identity.role.manage_created`

同时从内置 `project_owner` 默认权限中移除这些权限。其余管理员能力继续通过系统页面授权和 `system_admin` 身份判断控制。

### PostgreSQL 数据迁移

新增 Alembic 版本 `0021_remove_team_management`，升级时在同一事务中按依赖顺序清理：

1. 删除 `user_page_access` 中 `/review/users`、`/review/roles` 的记录；
2. 删除 `role_page_access` 中这两个路由的记录；
3. 先删除 `navigation:team:users`、`navigation:team:roles`，再删除 `navigation:team`；
4. 删除七个权限代码对应的角色授权和权限依赖；
5. 删除权限目录记录。

迁移不修改用户、用户角色、普通角色或业务数据。降级只恢复系统目录定义和内置项目负责人原始权限，不尝试恢复升级前无法准确重建的账号级、角色级页面授权。

### 多系统管理员契约

系统目前没有“最多一个系统管理员”的约束，管理接口已经允许为其他账户分配 `system_admin`。本次不添加无意义的生产代码改动，而是补充并固定以下行为契约：

- 系统管理员可以把 `system_admin` 分配给第二个及后续账户；
- 分配新管理员不会移除原管理员角色；
- 多个管理员可以同时处于启用状态；
- 只有 `role_codes` 包含 `system_admin` 的账户获得管理员身份；
- 移除角色、停用或删除账户时，仍不得使有效系统管理员数量降为零。

## 错误处理与兼容性

- 旧页面 `/review/users`、`/review/roles` 返回 404。
- 所有 `/api/team/*` 请求返回 404。
- 已登录会话不需要强制失效；下一次请求会使用更新后的权限和页面目录。
- 数据库尚未升级至新 Alembic head 时，应用继续遵循现有数据库版本检查策略，不增加启动时隐式清理。
- 当前运行中的 8899、8900 服务不在本次修改过程中停止或重启。

## 测试策略

采用测试驱动方式完成：

1. 先将团队管理相关路由、目录和页面 API 契约测试改为“条目不存在、请求 404”，确认在删除前失败。
2. 增加权限目录测试，确认七个专用权限不再存在，且所有导航项都不再引用它们。
3. 增加迁移测试，在旧结构中插入团队导航、页面授权和权限数据，升级后确认全部被清除，同时普通用户、角色和其他页面授权保持不变。
4. 增加管理员角色分配测试，确认第二个账户可以获得 `system_admin`，并确认最后一个管理员保护仍生效。
5. 运行定向测试、Alembic 空库升级、完整 `tests/` 和 `pre-commit run --all-files`。

## 验收标准

- 源码中不存在团队 API 构建器和 `/api/team/*` 注册。
- 页面、导航和页面授权目录中不存在 `/review/users`、`/review/roles`。
- 权限目录及数据库中不存在七个团队专用权限。
- 旧页面和 API 返回 404，而系统用户、角色和导航管理正常。
- 系统管理员可分配给多个账户，`"*"` 不产生管理员身份，最后管理员保护保持有效。
- 数据迁移、定向测试、完整测试和提交前检查全部通过。
