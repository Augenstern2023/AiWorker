# AiWorker 本机管理能力扩展方案

## 1. 目标与边界

在不引入 FEBS 的 Java/Shiro 技术栈、也不新增会话管理的前提下，为
AiWorker 的本机 WebGUI 补齐四项后台治理能力：

1. 组织/部门树、用户部门归属和项目成员角色。
2. 可筛选、可导出的管理审计中心。
3. 以现有权限目录为依据的可配置导航。
4. 基于现有 `JobManager` 的本机任务调度、重试、并发限制、执行记录和告警。

本方案只面向单机常驻的 WebGUI 进程。系统库将从 SQLite 迁移至本机
PostgreSQL 17.10；不设计跨机器抢占、分布式锁、集群调度或外部消息队列。
采集数据、RAG 本地索引和任务运行时状态继续使用其现有的独立存储。

## 2. 现状与原则

现有系统已具备用户、角色、权限、会话、项目成员、工作流和审计数据模型。
权限服务支持 `task`、`project`、`managed_projects`、`all` 四种数据范围；
`NavigationService` 负责根据有效权限显示静态导航；`JobManager` 负责启动、
监控、暂停、恢复、重试和持久化单次任务状态。

因此，本次扩展遵循以下原则：

- 权限唯一来源：继续使用 `identity` 的角色和权限体系，不复制一套菜单权限。
- 页面和 API 的授权独立于导航：导航只控制可见性，绝不作为访问控制手段。
- 项目角色与部门职务分离：`project_members` 只描述项目协作身份。
- 调度配置和执行记录可恢复：WebGUI 重启后恢复启用的计划，保留历史记录。
- 本机优先：避免为单机需求引入队列、服务注册、分布式锁或第二个后台服务。
- 敏感信息不进入审计或调度参数展示；沿用现有审计脱敏规则。

## 3. 方案对比与结论

### 方案 A：原生扩展现有 FastAPI 模块

新增组织、导航和调度服务，审计服务在现有基础上扩展查询导出；所有模块共享
当前系统数据库和权限服务。

优点：业务边界清晰，无双账号和双权限问题，能直接复用现有模板、路由、审计和
`JobManager`。缺点：需要补齐管理界面与迁移测试。

### 方案 B：独立部署传统后台系统

将 FEBS 或同类后台作为旁路系统，另行维护用户、角色、菜单与日志。

优点：传统后台页面较完整。缺点：身份、权限、项目成员和审计会分裂，且 FEBS 的
依赖栈陈旧，与当前 FastAPI 应用不兼容。

### 方案 C：只增加管理页面

在现有页面上临时展示部门、审计和任务信息，但不建立持久化模型和服务接口。

优点：初期工作量最小。缺点：组织关系、调度定义和执行历史无法可靠恢复，也无法
形成可测试的业务边界。

结论：采用方案 A。

## 4. 总体架构

```text
WebGUI 生命周期
  ├─ IdentityRepository / PermissionService
  │    ├─ 部门与用户归属
  │    ├─ 项目成员角色
  │    └─ 可配置导航项
  ├─ AuditService
  │    └─ 查询、导出、操作留痕
  └─ LocalScheduleService
       ├─ APScheduler BackgroundScheduler
       ├─ schedule_definitions / schedule_runs
       └─ JobManager.create_job()
            └─ Worker 进程、事件、产物、单次任务状态
```

`IdentityRepository` 继续是用户、角色、权限、部门和导航配置的主存储入口，但其
底层连接会收敛为 PostgreSQL 系统数据库访问层。`AuditService` 继续写入统一的
`audit_logs`。调度模块只创建和跟踪任务，不复制 `JobManager` 的进程监控、任务
文件、事件和产物逻辑。

## 5. 组织与项目成员

### 5.1 数据模型

新增 `departments`：

| 字段 | 含义 |
| --- | --- |
| `id` | TEXT 主键，存储标准 UUID 字符串 |
| `name` | 同一父部门下唯一的部门名称 |
| `parent_id` | 父部门，可为空表示根部门 |
| `sort_order` | 同级显示顺序 |
| `status` | `active` 或 `disabled` |
| `created_at` / `updated_at` | 审计与排序辅助时间 |

新增 `user_departments`：

| 字段 | 含义 |
| --- | --- |
| `user_id` | 现有用户 |
| `department_id` | 部门 |
| `is_primary` | 是否主部门；每个用户最多一个主部门 |
| `created_at` | 归属建立时间 |

保留现有 `project_members(project_id, user_id, project_role, status, ...)`。
它表示某用户在某项目中的协作身份，例如负责人、策划或编剧；部门不自动授予
项目访问权，也不改变既有数据范围判定。

### 5.2 服务与规则

新增 `DepartmentService`，负责创建、改名、移动、停用、列树、维护用户归属。

- 移动部门前验证目标父节点不是当前节点或其后代，避免树形成环。
- 非空部门不能直接删除；先迁移子部门和用户归属，或将其停用。
- 被停用部门不允许新增归属，但保留历史归属数据。
- 一个用户可属于多个部门；主部门只能有一个，设置新主部门时在同一事务内取消旧值。
- 部门及用户归属的新增、修改、停用均写入 `audit_logs`。

### 5.3 管理界面

系统管理新增“组织架构”页面：左侧为树，右侧为部门详情和成员列表。用户管理页
提供部门归属编辑；项目成员页继续只编辑项目角色，不混入部门字段。

所需权限以新权限码表达，例如 `department.read`、`department.manage`。页面路由和
API 分别声明所需权限，导航仅据此显示入口。

## 6. 管理审计中心

### 6.1 查询能力

复用 `audit_logs` 及 `AuditService.query()`，扩展下列组合筛选条件：

- 操作人：用户 ID、用户名或显示名。
- 项目：项目 ID。
- 动作：本阶段按精确动作筛选，例如 `workflow.claim`；动作前缀匹配留待具备
  索引和产品需求后单独扩展，避免把模糊查询混入首版管理页。
- 结果：`success`、`failure`。
- 时间：开始时间（含）与结束时间（不含）。
- 目标：资源类型、资源 ID，用于排查单个任务或部门变更。

审计查询响应固定返回 `actor_user_id` 与 `actor_display_name`。新审计事件在写入时保存
`actor_display_name_snapshot`；查询优先使用快照，旧记录则左连接 `users` 回填显示名，
仍无法取得名称时回退显示用户 ID。这样用户改名、停用或软删除不会改写已发生的审计
事实。

查询结果按 `created_at DESC, id DESC` 排序，并限制单次返回量；前端使用明确的页码
和每页条数，避免一次性加载完整审计库。

### 6.2 导出能力

提供 CSV 与 XLSX 两种导出：

- CSV 使用 UTF-8 with BOM，保证 Excel 打开中文不乱码。
- XLSX 使用项目既有 `openpyxl` 依赖。
- 导出沿用审计数据中已脱敏的摘要字段，不额外读取密码、token、cookie、密钥或
  原始请求体。
- 导出文件名包含筛选时间范围和生成时间；导出操作本身记录为 `audit.export`。
- 仅拥有 `audit.read` 的系统管理员可查看和导出全量审计；项目负责人只可查看其
  管理项目的记录，并且不能导出超出项目范围的数据。

Alembic 审计迁移新增上述名称快照列，并对历史记录按迁移时的用户资料一次性回填。
运行时查询仍左连接 `users` 作为缺失快照的兼容回退，最终回退为用户 ID；前端统一
显示 `actor_display_name`，不读取不存在的 `actor_username` 字段。

本阶段接口固定为 `GET /api/admin/audit` 和 `GET /api/admin/audit/export`。二者共用
`actor`（用户 ID、用户名或显示名）、`project_id`、`action`、`result`、`created_from`
和 `created_to` 筛选参数；开始时间包含、结束时间不包含。列表每次最多返回 500 条，
导出也采用该上限，避免单机 WebGUI 因无界下载耗尽内存。导出端点仅接受 `csv` 或
`xlsx`，在生成数据后另写一条 `audit.export` 记录，因此导出文件不包含本次导出自身。

对仍在 SQLite 运行的本期代码，`AuditRepository` 启动时幂等补齐
`actor_display_name_snapshot` 并回填旧记录；对 PostgreSQL 公共基础，新增独立 Alembic
revision，而不改变既有 `TEXT` 主键/外键约定。所有筛选值使用固定列和绑定参数，用户
输入不参与 SQL 标识符拼接。

### 6.3 管理界面

“审计日志”页提供固定筛选栏、结果表格、详情侧栏和导出按钮。详情仅展示脱敏后的
变更前后摘要、请求 ID、IP、用户代理、操作原因与结果，不渲染原始 JSON 为 HTML。

## 7. 可配置导航

### 7.1 数据模型

新增 `navigation_items`：

| 字段 | 含义 |
| --- | --- |
| `id` | TEXT 主键，存储标准 UUID 字符串 |
| `parent_id` | 父导航项，可为空 |
| `label` | 显示名称 |
| `icon` | Bootstrap Icon 名称 |
| `route` | 站内页面路由 |
| `required_permission` | 可见导航所需的现有权限码 |
| `sort_order` | 同级顺序 |
| `is_enabled` | 是否显示 |
| `is_system` | 内置导航，禁止删除 |

初始迁移将 `NAVIGATION_CATALOG` 的栏目和子项导入该表，保证当前导航顺序和入口不变。

### 7.2 授权边界

`NavigationService.items_for()` 从启用的配置中构建可见项，依据
`required_permission` 与 `Principal.permissions` 过滤。导航项没有权限定义权：

- 路由页面继续由 `require_page()` 保护。
- API 继续由路由依赖或明确的权限检查保护。
- 新导航项的 `required_permission` 必须是权限目录中已登记的权限码。
- 配置一个没有对应页面路由的入口时，保存失败；删除或停用导航项不会撤销页面访问。

这样可避免“知道 URL 就绕过菜单”的传统后台授权问题。

### 7.3 管理界面

系统管理新增“导航配置”页，支持排序、启停、编辑标签和图标。内置项的路由和所需
权限不可由页面修改；新增自定义入口仅允许指向已登记的内部页面。每次变更写入审计。

## 8. 本机任务调度

### 8.1 调度模型

新增 `schedule_definitions`：

| 字段 | 含义 |
| --- | --- |
| `id` | TEXT 主键，存储标准 UUID 字符串 |
| `name` | 本机唯一计划名称 |
| `job_type` | 白名单任务类型 |
| `payload_json` | 经校验的任务参数 |
| `trigger_type` | `cron` 或单次 `date` |
| `trigger_config_json` | cron 字段或执行时间 |
| `timezone` | 固定为 `Asia/Shanghai` |
| `is_enabled` | 是否参与调度 |
| `max_retries` | 失败后最多重试次数，默认 3 |
| `misfire_policy` | 默认 `skip`，错过时间不补跑 |
| `created_by` / `updated_by` | 配置责任人 |

新增 `schedule_runs`：

| 字段 | 含义 |
| --- | --- |
| `id` | TEXT 主键，存储标准 UUID 字符串 |
| `schedule_id` | 对应计划 |
| `job_id` | `JobManager` 创建的任务 ID |
| `attempt` | 首次执行为 1，重试递增 |
| `status` | `queued`、`running`、`succeeded`、`failed`、`skipped`、`cancelled` |
| `scheduled_at` / `started_at` / `finished_at` | 触发与执行时间 |
| `error_summary` | 截断且脱敏后的失败摘要 |
| `retry_of_run_id` | 上一次尝试，首次为空 |

### 8.2 运行机制

WebGUI 生命周期创建 `LocalScheduleService` 并启动 APScheduler 的
`BackgroundScheduler`。应用启动时从 `schedule_definitions` 读取已启用计划并注册
触发器。`LocalScheduleService.shutdown()` 只停止新的触发和待执行的重试，不直接终止
已经交给 `JobManager` 的任务；但 WebGUI 的完整进程关闭沿用现有行为，会调用
`JobManager.stop()` 终止运行中的任务。调度服务在此之前将关联的运行记录标记为
`cancelling`，并在任务终态回收后写为 `cancelled`，不把进程关闭误记为任务失败。

调度器仅接受明确白名单中的任务类型：爬取、榜单更新、素材下载及其已有分析任务。
`payload_json` 通过对应的 Pydantic 请求模型校验后才能保存或启动。计划触发时执行：

1. 创建 `schedule_runs` 记录。
2. 检查同一计划是否已有 `queued` 或 `running` 记录；存在则本次记为 `skipped`。
3. 调用 `JobManager.create_job()`，并在任务 `extra` 中写入 `schedule_id` 和
   `schedule_run_id`。
4. 监听或轮询对应 `job_id` 的终态，将 `JobManager` 的结果回写到 `schedule_runs`。
5. 失败且未超过重试次数时，分别在 1、5、15 分钟后建立一次性重试触发器。

现有 `JobManager` 的平台冲突检查仍是执行层最后一道并发保护；调度层额外保证同一
计划不重入。调度计划的新增、修改、停用、手动运行、重试、取消和失败均写入审计。

### 8.3 告警与管理界面

本机告警不接入邮件、短信或第三方 Webhook。系统后台提供“调度中心”页面，展示：

- 启用状态、下次执行时间、最近执行结果和连续失败次数。
- 运行中/失败计划的数量徽标。
- 失败记录的错误摘要和关联 `job_id`，可跳转既有任务详情与日志。
- 手动运行、暂停计划、恢复计划和立即重试按钮。

失败告警通过管理页醒目状态、系统日志和审计记录形成闭环；连续失败达到三次时，
计划自动暂停，等待管理员处理，避免持续消耗本机资源。

## 9. PostgreSQL 17.10 系统库迁移

### 9.1 版本与迁移范围

目标数据库为已安装的 **PostgreSQL 17.10（Windows x86-64）**，以本机服务方式运行。
系统库使用独立数据库 `aiworker_system` 和最小权限应用账号 `aiworker_app`；应用仅可
访问该数据库和必要 schema，不使用 PostgreSQL 超级用户运行 WebGUI。

本期迁移范围为当前 `.runtime/system/system.db` 承载的系统数据：

- 用户、角色、权限、用户角色、权限依赖和项目成员。
- 工作流实例、任务、任务事件、提交、审批及项目成员事件。
- 审计日志。
- 本方案新增的部门、用户部门归属、导航项、调度定义和调度执行记录。

以下数据不在本期范围内，继续使用已有存储并通过业务 ID 关联：

- 爬虫采集结果及 `database/` 下的 SQLite/MySQL 数据库。
- `creative`、`analysis` 的独立 SQLite 数据库。
- `.runtime/agent_state.db`、任务 JSON、日志和产物文件。
- Chroma/RAG 本地向量索引。

### 9.2 目标访问架构

新增 `SystemDatabase` 访问层，用同步 SQLAlchemy Core 管理系统库连接和事务；现有
WebGUI、身份、权限、工作流与审计服务均经由该层获得连接。选择同步 Core 是为了匹配
当前同步仓储方法和 FastAPI 中的同步业务调用，避免在本次迁移中同时引入 async ORM
改造风险。

数据库连接只从环境变量读取：

```text
AIWORKER_SYSTEM_DATABASE_URL=postgresql+psycopg://aiworker_app:<password>@127.0.0.1:5432/aiworker_system
```

密码不写入 `config/*.py`、前端代码、调度参数或 Git；本机可放在未纳入版本控制的
`.env`。Python 依赖固定为 `psycopg[binary]>=3.2,<4`、现有 SQLAlchemy 2.x 和
Alembic。数据库 schema 由 Alembic 版本化管理，运行时不再以
`CREATE TABLE IF NOT EXISTS`、`ALTER TABLE` 或 SQLite PRAGMA 方式补表。

所有系统库 SQL 改为 SQLAlchemy `text()` 的命名参数，消除 SQLite 的 `?` 占位符、
`sqlite3.Row`、`BEGIN IMMEDIATE` 和 SQLite 专属异常类型依赖。查询行以
`RowMapping`/字典形式转换；事务由 `SystemDatabase.transaction()` 提供，并保持当前
服务层的“一个业务操作一个原子事务”语义。

PostgreSQL schema 使用：

- 系统表主键和外键继续使用 `TEXT`。现有 ID 包含 `role:<code>`、`workflow:system`
  等非 UUID 值，SQLite 导入必须字节语义保留，不得隐式重写为 PostgreSQL `UUID`。
  新增部门、导航和调度实体可用 `uuid.uuid4()` 生成，但以标准字符串写入 `TEXT` 列。
- `TIMESTAMPTZ` 保存会话、审计、工作流和调度时间。
- `JSONB` 保存事件详情、审计摘要和调度参数。
- 外键、检查约束和部分唯一索引保证静态数据完整性，例如每用户只有一个主部门、同一
  计划不存在并发执行记录。
- “至少存在一个启用的系统管理员”及“全局唯一项目负责人”继续由事务性服务校验保证；
  相关查询在 PostgreSQL 中使用行锁，避免并发更新同时移除最后一个有效负责人。

### 9.3 数据迁移与切换流程

迁移采用一次性维护窗口，不做双写和长期 SQLite/PostgreSQL 并行运行。执行顺序为：

1. 仅在最终切换时进入维护窗口：暂停 WebGUI 的写入入口与调度触发，等待运行中的
   `JobManager` worker 自然结束。迁移期间禁止创建、取消或重试业务任务；开发、测试、
   Alembic 编写和 PostgreSQL 测试库验证阶段不需要暂停当前服务。
2. 若 worker 在维护窗口截止前未结束，由管理员显式停止；其关联调度运行记录记为
   `cancelled`。确认没有活跃系统库写入后，再停止 WebGUI 进程。
3. 对 `.runtime/system/system.db` 做只读备份，并校验备份可打开；记录每张待迁移表的
   行数和关键业务统计。
4. 在 PostgreSQL 临时 schema 上执行 `alembic upgrade head`，再运行专用迁移命令。
   迁移按外键依赖顺序复制权限目录、用户、角色、授权关系、项目成员、工作流、审批和
   审计日志；JSON 文本校验后写入 `JSONB`。
5. 不复制旧 `sessions` 的原始 token。切换后所有用户重新登录，避免旧会话散列、CSRF
   派生值与新数据库状态交叉使用。
6. 校验迁移后的表行数、主外键完整性、唯一约束、管理员角色、项目成员、工作流状态及
   审计抽样记录；执行只读权限与项目访问冒烟测试。
7. 验证通过后，将 `AIWORKER_SYSTEM_DATABASE_URL` 指向 PostgreSQL，重启 WebGUI，
   运行数据库健康检查并创建新的登录会话。

切换失败时，仅在 WebGUI 尚未对 PostgreSQL 接受写入前回滚：停止程序、恢复旧 SQLite
配置并从备份启动。切换成功后 SQLite 备份只作为归档，不做反向同步；任何回滚必须使用
完整备份恢复，禁止人工复制部分表或部分记录。

### 9.4 与调度中心的关系

`LocalScheduleService` 仅在 PostgreSQL 健康检查成功且 Alembic 版本处于 `head` 后启动。
`schedule_definitions` 与 `schedule_runs` 由 PostgreSQL 持久化，保证 WebGUI 重启后计划、
失败次数和执行历史可恢复；一次任务仍由本地 `JobManager` 执行并以 `job_id` 回写运行记录。

如果 PostgreSQL 不可连接、迁移版本落后或 schema 校验失败，WebGUI 应记录明确错误并
禁用调度器，不得退回 SQLite 创建第二套系统库，也不得静默丢弃调度记录。

### 9.5 备份、监控与验证

- 每次升级前执行 `pg_dump --format=custom` 备份 `aiworker_system`，保留 SQLite 原始
  备份直到 PostgreSQL 上稳定运行并完成验收。
- WebGUI 健康检查显示数据库连通性、当前 Alembic revision、连接池状态和最近备份时间；
  不显示数据库密码或完整连接串。
- 单元测试保留 SQLite 迁移源样本；集成测试使用独立 PostgreSQL 测试库，覆盖 Alembic
  升级、迁移幂等性、事务回滚、约束、权限、审计筛选及调度重入。
- 测试数据库 URL 必须与本机业务库不同，例如 `aiworker_system_test`；测试结束清理其
  schema，不连接或清理正式 `aiworker_system`。

## 10. 实施顺序

### 第零阶段：系统库 PostgreSQL 化

1. 建立 PostgreSQL 17.10 本机数据库、最小权限账号、`.env` 配置和连接健康检查。
2. 引入 `psycopg`、配置 Alembic，并以版本化 migration 重建现有系统库 schema。
3. 建立 `SystemDatabase`，逐步替换 `identity`、`workflow`、`audit` 中的 SQLite 专属
   连接、SQL 和异常处理；保持对旧 SQLite 文件的只读导入能力。
4. 编写 SQLite 到 PostgreSQL 的迁移命令、迁移前检查、迁移后校验和失败回滚演练。
5. 在 `aiworker_system_test` 上完成完整测试，再在维护窗口完成正式切换。

### 第一阶段：组织与项目协作边界

1. 新增部门和用户部门归属表、迁移逻辑、仓储服务和单元测试。
2. 新增组织架构 API、系统管理页面和部门权限。
3. 验证部门树无环、主部门唯一、停用规则和项目成员角色不受影响。

#### 第一阶段当前交付：PostgreSQL 组织数据模块

当前功能分支只交付第一阶段的持久化与服务边界，不提前切换 WebGUI 的
SQLite 运行时来源，也不包含组织页面、HTTP API、权限目录、导航配置、审计中心或
调度中心。这样可以在已批准的 PostgreSQL 公共基础之上，先验证组织数据约束；后续
身份与工作流仓储完成 PostgreSQL 适配后，再把本模块接入请求链路。

具体实施如下：

1. 在 `system_database.schema.SYSTEM_METADATA` 中定义 `departments` 与
   `user_departments`，并新增独立 Alembic revision。历史 `0001` 基线只创建其发布时
   的表；新表只由新 revision 创建，避免未来执行旧 revision 时意外包含后续表。
2. 所有主键和外键继续为 `TEXT`。部门 ID 由服务以标准 UUID 字符串生成；既有
   `users.id`、`project_members.id`、`project_id` 和 `user_id` 不转换为 UUID 类型。
3. `departments` 使用自引用 `parent_id`、同父节点名称唯一约束和同级排序索引；状态只
   允许 `active` 或 `disabled`。`user_departments` 以 `(user_id, department_id)` 为主键，
   使用 PostgreSQL 部分唯一索引保证同一用户最多一条 `is_primary = true` 的归属。
4. 新增 `organization.DepartmentService`，只依赖 `SystemDatabase` 和 SQLAlchemy Core。
   它提供创建、重命名、移动、停用、树形查询、设置用户部门以及列出用户部门的接口。
   创建或移动时拒绝不存在的父节点、当前节点和任何后代节点；停用非空部门时拒绝；
   停用部门拒绝新增用户归属；设置新的主部门在同一事务内清除旧主部门。
5. 项目成员角色仍由既有 `project_members(project_id, user_id, project_role, status, ...)`
   表和 `WorkflowRepository` 管理。本阶段只通过 `DepartmentService` 的只读查询暴露
   项目成员角色，明确验证部门归属写入不会修改任何项目成员行、角色值或工作流状态。
   不增加角色枚举或数据库检查约束，因为现有项目角色与可配置业务角色并非固定集合。
6. 用 TDD 新增 PostgreSQL 集成测试：先验证表、部分唯一索引和服务导入失败，再实现
   最小代码；随后覆盖树环路、停用规则、多部门唯一主部门和项目角色隔离。测试只使用
   `AIWORKER_TEST_SYSTEM_DATABASE_URL`，绝不连接或清理 `aiworker_system`。

本交付不改变 `WorkflowStateMachine`、既有工作流状态值、状态迁移规则或已有测试文件。
组织变更审计、部门权限和 WebGUI/API 接入依赖 PostgreSQL 身份与审计仓储适配，保留在
第一阶段的后续提交中，避免在当前 SQLite/ PostgreSQL 双轨期间产生两套审计事实。

### 第二阶段：审计中心

1. 增加操作人显示名快照与 PostgreSQL revision；旧记录一次性回填，查询保留用户表
   左连接回退，保证改名后显示稳定且从不依赖 `actor_username`。
2. 扩展查询接口和项目范围授权，覆盖用户、项目、动作、结果及 `[from, to)` 时间窗。
3. 实现 CSV（UTF-8 BOM）/XLSX 导出和 `audit.export` 留痕；导出仅使用已脱敏摘要。
4. 增加筛选和下载页面；以 TDD 覆盖组合筛选、结束时间边界、改名后快照显示、两种
   导出格式和导出审计，不改变工作流状态机或既有工作流测试语义。

### 第三阶段：导航配置

1. 建立导航项表并从现有静态目录迁移初始数据。
2. 改造 `NavigationService` 为从持久化配置读取可见导航。
3. 实现导航配置页面；验证菜单隐藏不等同于路由失权，路由权限依旧生效。

### 第四阶段：调度中心

1. 引入 APScheduler，建立计划和执行记录表及服务。
2. 将 WebGUI 生命周期与调度器连接，定义白名单任务适配器。
3. 实现重入保护、重试退避、连续失败自动暂停和 `JobManager` 状态回写。
4. 实现调度中心页面、手动操作和失败告警展示。

每一阶段完成后均运行对应单元测试和 WebGUI 路由集成测试；完成四阶段后执行完整
`pytest` 与 `pre-commit run --all-files`。

## 11. 验收标准

- 管理员可维护多层部门、用户多部门归属和唯一主部门；非法移动和非空删除被拒绝。
- 项目成员角色与部门归属互不影响，既有工作流授权测试保持通过。
- 审计中心能按用户、项目、动作、结果和时间组合筛选，并导出脱敏的 CSV/XLSX。
- 菜单只向具备所需权限的用户显示；直接访问页面/API 仍由独立权限检查拒绝越权。
- WebGUI 重启后已启用计划恢复；每次运行都能关联到 `JobManager` 的 `job_id`。
- 同一计划不会并发重入；失败按 1/5/15 分钟最多重试三次，连续失败三次后自动暂停。
- 调度、组织、导航和审计导出操作均有可检索审计记录。
- 系统库运行于 PostgreSQL 17.10，且 WebGUI 不再以 SQLite 作为身份、权限、工作流或
  审计数据的运行时来源。
- SQLite 到 PostgreSQL 的迁移在测试库和正式库均通过行数、外键、关键权限及工作流
  校验；切换后用户被要求重新登录，旧系统库保持可恢复备份。
- 现有非 UUID 文本 ID 与新增 UUID 字符串均可写入同一 TEXT 键体系，导入前后 ID 值
  保持不变。
- 审计页面始终显示 `actor_display_name` 或用户 ID；历史操作人改名、停用或软删除后，
  审计显示和导出仍稳定。
- 关闭调度器不会发起新任务；完整 WebGUI 关闭会显式取消仍在执行的任务，并把关联
  调度运行记录收敛为 `cancelled`。
