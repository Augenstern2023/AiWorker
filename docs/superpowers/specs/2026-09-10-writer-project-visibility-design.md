# 编剧项目可见范围设计

## 背景

当前 `/writing/projects` 通过 `/api/creative/projects` 加载项目。普通编剧账号只要拥有
`project.read.established`，列表查询就会使用 `can_read_project` 展示全部已建立项目；进入项目后，
写操作又使用“已分配或可管理项目”校验，因此会出现列表可见、进入后却无法编辑的情况。

## 目标

- 系统管理员和全局项目负责人继续看到全部项目。
- 其他账号在编剧项目列表中只看到自己管理或已被分配的项目。
- 普通账号直接访问未管理、未分配项目的编剧页面时返回 403，不能绕过列表进入只读页面。
- 策划、审核等确实需要只读已建立项目的入口继续保留现有读取能力。

## 非目标

- 不改变项目成员、任务分配或项目负责人关系。
- 不收紧审核页面及其他业务场景对已建立项目的只读访问。
- 不改变各创作阶段内部的任务领取、编辑和锁定规则。

## 方案

### 项目列表

复用 `/api/creative/projects?participating_only=true`，将其定义为“当前账号可参与编辑的项目”：

- 系统管理员、`project_owner`：返回全部项目。
- 其他账号：仅返回 `can_access_assigned_project` 或 `can_access_managed_project` 为真的项目。

`/writing/projects` 的共享前端在加载项目时显式携带 `participating_only=true`。策划和审核入口仍可按
现有方式调用默认列表，不受本次修改影响。

### 直接访问

在页面路由层对带 `project_id` 的 `/writing/projects/...` 页面增加相同的项目范围校验：

- 系统管理员、全局项目负责人放行。
- 普通账号仅在项目已分配给本人或本人可管理时放行。
- 不满足时返回现有 403 页面，避免页面先渲染、随后写接口再报无权编辑。

API 原有的 `can_read_project` 保持不变，以免破坏审核、市场参考等只读场景；严格校验只应用于编剧页面
和编剧项目列表。

## 数据流

1. 编剧打开 `/writing/projects`。
2. 前端请求 `/api/creative/projects?participating_only=true`。
3. 后端按登录账号的系统身份、全局负责人身份、项目成员及管理关系过滤项目。
4. 编剧进入具体项目页面时，页面路由再次执行同一范围判定。
5. 阶段内的具体写操作继续执行既有任务及资源权限校验。

## 错误处理

- 身份权限服务缺失时拒绝访问，不以“展示全部”降级。
- 未分配、未管理项目的直接 URL 返回 403。
- 项目不存在时不返回项目内容；页面层可以统一按无范围权限返回 403，项目 API 保留既有 404 行为。

## 测试

- API：普通账号列表仅包含活动成员项目和可管理项目，不包含只有
  `project.read.established` 的项目。
- API：系统管理员与全局项目负责人在参与范围查询中仍可看到全部项目。
- 页面：普通账号不能直接打开未分配项目的 outline、Beats、场次剧本页面。
- 页面：已分配账号、项目管理员、全局项目负责人和系统管理员可打开对应编剧项目页面。
- 浏览器静态回归：编剧项目页请求带 `participating_only=true`，策划项目页保持原查询范围。
