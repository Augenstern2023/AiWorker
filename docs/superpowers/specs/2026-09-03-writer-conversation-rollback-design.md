# 编剧大师对话重新发送与系统回档设计

## 1. 背景

编剧大师的一轮对话不只产生聊天文本，还可能创建或关联原创项目、生成或编辑 Brief、人物、全剧大纲、Beats 与剧本、锁定版本、推进工作流任务，并产生持久化动作和后台任务。因此，删除消息或截断 `messages_json` 不能实现真正的“回档”。

本功能把一轮对话定义为“某条用户消息开始，直到下一条用户消息之前产生的回复、动作及系统变更”。用户点击某条历史用户消息的“回档”时，系统恢复到该消息发送前；该用户消息及其后的消息、报告、动作和项目修改均撤销。“重新发送”先执行同一回档，再使用新的消息 ID 重新处理原文。

## 2. 目标

- 历史用户消息支持“回档”和“重新发送”。
- 回档恢复会话、项目创作内容和工作流状态，而不是只改变页面显示。
- 生成的新内容从活动状态移除；被编辑或替换的内容恢复到回档前版本。
- 重新发送不复用旧幂等键，不会因旧 `message_id` 返回缓存结果。
- 跨 SQLite、PostgreSQL 和后台任务的回档可以重试、审计，并在外部修改冲突时安全停止。
- 页面完整处理确认、加载、冲突、失败、键盘、触屏和移动端状态。

## 3. 非目标

- 不提供任意时间点或任意数据库快照恢复。
- 不允许绕过当前项目权限、版本锁和工作流归属规则。
- 不覆盖从其他页面、其他会话或其他账户发生的后续修改。
- 不物理删除项目版本审计、动作审计或回档审计；只有回档创建且尚未被外部继续使用的新项目可调用现有项目删除补偿流程。
- 不让前端直接决定需要恢复的表、资源 ID 或项目 revision。

## 4. 已确认的回档边界

目标消息必须是已持久化且拥有检查点的用户消息。回档边界固定为该用户消息发送前：

```text
保留的上一轮状态
  ├─ 消息、报告和会话项目绑定
  ├─ 项目活动资源及项目 revision
  └─ 工作流任务状态

目标用户消息                    ← 撤销
目标消息的助手回复和动作          ← 撤销
之后的所有对话轮次、报告和动作     ← 撤销
上述动作实际写入的项目与工作流变更  ← 补偿恢复
```

“重新发送”使用相同边界完成回档后，以保存的原始文本和新的 `message_id` 创建一轮新对话。上传材料消息和系统生成消息不提供这两个入口。

## 5. 方案选择

采用“每轮检查点 + 每动作撤销记录 + 分阶段补偿协调器”。

- 会话检查点负责恢复消息、报告、绑定关系和会话 revision。
- 动作撤销记录在动作第一次写入项目之前保存受影响资源的前镜像，在动作完成后保存预期后镜像与 revision。
- 回档协调器按动作创建顺序倒序执行补偿，跨存储步骤写入持久化日志，失败后可从未完成步骤继续。

不采用仅截断聊天记录，因为项目状态不会恢复；不采用全库快照，因为会覆盖其他项目和其他用户的并发修改；不依赖模型生成反向操作，因为模型输出不具备可靠的事务和审计语义。

## 6. 数据模型

### 6.1 `writer_agent_turn_checkpoints`

新增不可变轮次检查点表：

| 字段 | 含义 |
| --- | --- |
| `id` | 检查点 ID |
| `session_id` / `actor_user_id` | 所属会话与发起账户 |
| `user_message_id` | 对应用户消息 ID，会话内唯一 |
| `turn_sequence` | 单调递增的轮次序号 |
| `message_count_before` | 发送前消息数量 |
| `report_count_before` | 发送前报告数量 |
| `session_snapshot_json` | 标题、项目绑定、上下文 revision、最新报告等会话前镜像 |
| `original_message_json` | 重新发送所需的原始文本和安全请求字段 |
| `status` | `open/completed/rolled_back/superseded` |
| 时间字段 | 创建、完成与回档时间 |

检查点在取得消息 claim 后、调用模型及创建任何候选动作之前写入。同一 `(session_id, user_message_id)` 重试只能返回原检查点，内容摘要不一致则沿用现有 `IDEMPOTENCY_KEY_REUSED` 语义。

### 6.2 动作归属与撤销记录

`writer_agent_actions` 增加可空 `turn_checkpoint_id`，历史动作保持为空且不可自动回档。新增 `writer_agent_action_undo`：

| 字段 | 含义 |
| --- | --- |
| `action_id` / `turn_checkpoint_id` | 动作与轮次归属 |
| `project_id` | 受影响项目，可空 |
| `preimage_json` | 写入前的项目、资源活动指针和受影响行摘要 |
| `postcondition_json` | 动作完成后的 project revision、资源指纹和工作流状态 |
| `workflow_preimage_json` | 受影响任务和提交状态的前镜像 |
| `status` | `prepared/applied/compensated/conflict` |
| 时间字段 | 准备、完成与补偿时间 |

前镜像只覆盖白名单动作实际影响的项目、资源与任务。新建版本的补偿方式是恢复活动指针并把新版本标记为 `superseded`；编辑已有草稿时恢复原字段并形成审计事件；新建项目仅在后置条件仍匹配且没有外部引用时调用现有项目删除补偿流程。

### 6.3 `writer_agent_rollbacks`

回档请求使用 `(session_id, client_request_id)` 幂等。记录目标检查点、模式 `rollback/resend`、当前阶段、影响摘要、错误码和完成时间。阶段固定为：

```text
requested → jobs_settled → validated → creative_restored
          → workflow_restored → conversation_restored → completed
```

跨库处理中断时不提前截断对话；重试从最后一个持久化阶段继续。页面只有在 `completed` 后切换到恢复后的会话。

## 7. 服务端流程

### 7.1 创建和完成检查点

消息接口在新消息 claim 成功后创建检查点，记录消息和报告边界、会话项目绑定及原始请求。模型响应、候选动作和报告保存完成后将检查点标记为 `completed`。失败但未产生系统写入时检查点保留，支持同一客户端请求按既有 claim 规则恢复。

动作创建时从当前消息处理上下文写入 `turn_checkpoint_id`。自然语言确认或按钮确认旧动作时仍归属于最初生成该动作的轮次，不归属于点击确认时的最新轮次。

### 7.2 回档预览

```http
GET /api/writer-agent/sessions/{session_id}/messages/{message_id}/rollback-preview
```

返回服务端计算的消息数、报告数、动作数、受影响项目内容数、运行中任务数、目标项目和当前是否可执行。无检查点、无权限、历史动作无法补偿或已发现 revision 冲突时返回稳定原因，不泄露无权读取的资源内容。

### 7.3 执行回档

```http
POST /api/writer-agent/sessions/{session_id}/messages/{message_id}/rollback
```

请求包含 `client_request_id` 和预览返回的 `expected_history_revision`。协调器依次执行：

1. 校验会话写权限、目标检查点和历史 revision。
2. 选出目标检查点及其后的全部轮次和动作。
3. 对排队或运行中的动作请求取消；任务未进入终态时返回 `ROLLBACK_BUSY`，不开始数据补偿。
4. 按动作倒序校验当前项目 revision、资源指纹、活动指针和工作流状态是否仍等于记录的后置条件。
5. 任一外部变化返回 `ROLLBACK_CONFLICT`，不覆盖当前内容。
6. 在创作库事务中恢复前镜像或撤销新建资源。
7. 补偿工作流任务和提交状态，并追加回档事件。
8. 在 Writer Agent SQLite 事务中恢复会话前镜像，截断消息与报告，把受影响动作标记为 `rolled_back`，使后续检查点失效。
9. 写入完成审计并返回刷新后的完整会话。

重复请求返回同一结果。已完成回档再次执行不重复恢复资源。

### 7.4 重新发送

```http
POST /api/writer-agent/sessions/{session_id}/messages/{message_id}/resend
```

请求同样包含 `client_request_id` 和 `expected_history_revision`。服务端先完成上述回档，再从目标检查点读取原始消息，以新生成的客户端消息 ID 调用与普通消息相同的内部处理入口。响应返回新消息 ID 和更新后的完整会话。

如果模型调用在回档完成后失败，系统保持已回档状态并返回可重试错误；再次使用同一 `client_request_id` 只重试新消息处理，不重复执行补偿。

## 8. 并发、权限与错误处理

- 会话增加 `history_revision`，保存新轮次、材料、项目绑定和成功回档时递增；预览和提交必须比较该值。
- 同一会话同一时刻只允许一个消息处理或回档协调器持有写租约。
- 回档需要现有会话写权限，并在执行时重新校验每个受影响项目的写权限；页面访问权本身不替代项目数据权限。
- 历史动作没有撤销记录时，对涉及项目写入的轮次禁用回档；纯消息历史仍可回档。
- 已被其他入口继续修改的项目不尝试自动合并，返回冲突并保留全部现状。
- 项目创建、生成和工作流后台任务只有确认已停止或已完成后才能补偿。
- 日志和 API 不返回模型密钥、Cookie、完整材料快照或其他账户的数据。

稳定错误码包括：

- `TURN_CHECKPOINT_NOT_FOUND`
- `TURN_ROLLBACK_UNSUPPORTED`
- `HISTORY_REVISION_MISMATCH`
- `ROLLBACK_BUSY`
- `ROLLBACK_CONFLICT`
- `ROLLBACK_PERMISSION_DENIED`
- `ROLLBACK_PARTIAL_FAILURE`

`ROLLBACK_PARTIAL_FAILURE` 表示跨库补偿在某阶段失败，协调器保留阶段日志，用户可重试；不得把它伪装为成功或提前隐藏对话。

## 9. 页面与交互

每条具有检查点且已完成的用户消息右下方显示两个紧凑文本图标按钮：“重新发送”和“回档”。沿用页面现有 Bootstrap Icons、颜色、圆角和按钮体系，不引入新依赖。

- 按钮使用原生 `button`，带 `aria-label`、`title` 和可见焦点。
- 悬停、键盘聚焦和触屏点击都能操作；移动端按钮保持可见，不依赖 hover 才出现。
- 当前消息正在处理、回档正在执行、检查点不完整或预览判定不可执行时禁用按钮。
- 点击“回档”先请求预览，再显示确认弹窗，列出将撤销的消息、动作和项目内容数量。
- 点击“重新发送”使用同一确认弹窗，额外说明原文会用新消息 ID 再次发送。
- 执行时目标消息按钮显示加载态，其他发送、动作确认、回档和重发入口统一禁用，避免交叉写入。
- 成功后用接口返回值一次性刷新会话列表、对话、报告、项目上下文和动作卡，不追加临时重复消息。
- `ROLLBACK_BUSY` 提示任务正在停止，可重试；冲突错误明确提示项目已从其他入口更新，不自动覆盖。
- 确认弹窗关闭后焦点返回原按钮，Escape 可关闭；状态变化通过现有 `aria-live` 区域播报。
- `prefers-reduced-motion` 下不增加新的位移动画。

## 10. 测试与验收

### 10.1 Store 与协调器测试

1. 检查点在模型和动作副作用前创建，同 message ID 重试保持幂等。
2. 纯消息回档恢复消息、报告和最新报告边界。
3. 目标轮次之后的 pending、failed、succeeded 和 retry-chain 动作全部失效且不可继续操作。
4. 新建项目回档后项目不可见，关联已有项目回档后恢复原绑定。
5. Brief、人物、大纲、Beats 和剧本的新建、编辑、选择与锁定均恢复前镜像，新版本保留为 `superseded` 审计历史。
6. 工作流任务、提交与成员副作用按前镜像恢复并追加事件。
7. 当前 revision 或资源指纹与后置条件不一致时，在任何补偿前返回冲突。
8. 运行中 Job 未停止时返回 busy，不截断消息。
9. 跨库步骤失败后，相同请求可从阶段日志幂等续跑。
10. 重新发送生成新的消息 ID；模型失败后不会重复回档。

### 10.2 API 与权限测试

- 预览数量和可执行状态准确。
- 非会话所有者、失去项目写权限者和伪造 message ID 的请求被拒绝。
- `expected_history_revision` 过期时返回 409。
- 重复 `client_request_id` 返回同一回档结果。
- 旧会话纯消息允许兼容回档；缺少动作撤销记录的项目写入历史明确禁用。
- 普通消息 claim、动作确认、失败重试和项目审核接口无回归。

### 10.3 浏览器测试

- 只有可操作的用户消息显示按钮，材料和助手消息不显示。
- 确认弹窗展示服务端影响摘要，取消不发送回档请求。
- 加载期间按钮禁用且不会重复提交。
- 成功后消息、报告、项目栏和动作卡同步恢复。
- busy、revision 冲突、权限失败和网络失败均显示可理解提示。
- 桌面与窄屏下按钮不遮挡消息；Tab、Enter、Space、Escape 和焦点返回正确。

## 11. 兼容与发布

- 新表和新字段由现有 SQLite 启动迁移创建，旧行使用安全默认值。
- 会话响应只增加 `history_revision` 和消息的派生 `turn_controls`，旧客户端可忽略。
- 原消息接口、动作接口和项目页面 URL 保持不变。
- 首次发布后，新轮次立即拥有完整回档能力；旧纯消息轮次可依据边界生成兼容检查点，涉及无法证明后置条件的旧项目写入不开放强制回档。
- 回档审计保留目标消息 ID、操作者、影响资源引用、冲突与阶段状态，不保存敏感正文副本。

## 12. 验收结论

本功能以“恢复到目标用户消息发送前”为唯一回档语义。任何无法证明当前系统仍处于该轮动作后置状态的情况都停止并提示冲突；不会为了让聊天界面看起来已回档而覆盖外部修改或隐藏尚未恢复的系统状态。
