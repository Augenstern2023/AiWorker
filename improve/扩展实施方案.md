# AiWorker B站分析链路扩展实施方案

## 一、目标与边界

### 1.1 扩展目标

在不破坏当前 AiWorker 多平台爬虫架构的前提下，把现有 B站采集能力扩展为一条可用于 Trove AI / Markdown 知识库 / 本项目数据分析的内容处理链路：

```text
B站链接 / BV号 / 关键词 / UP主
        ↓
AiWorker B站采集
        ↓
视频元数据 + 评论 + 字幕 / 音频
        ↓
字幕解析或 ASR 转写
        ↓
LLM 摘要 / 要点 / 标签 / 风险提示
        ↓
Markdown / JSON / Trove 导出
```

### 1.2 推荐架构

推荐采用“采集层与分析层分离”的方式：

- `media_platform/bilibili/` 继续负责 B站登录、搜索、详情、评论、播放地址、媒体下载。
- 新增 `analysis/` 目录负责字幕、ASR、LLM、导出。
- 初期优先输出 Markdown / JSON 文件，不先改数据库结构。
- Trove AI 先走 Markdown 文件级兼容，确认 API schema 后再做 API 推送。

### 1.3 不建议一开始做的事

- 不建议把 AiWorker 和 Trove AI 硬合并。
- 不建议直接写 Trove 的 PostgreSQL / pgvector 表。
- 不建议第一阶段就接 WebGUI、RAG、向量库和多平台视频分析。
- 不建议无差别下载完整视频，优先抓字幕，其次只下载音频。

## 二、现状基础

当前项目已经具备 B站采集基础：

| 能力 | 当前状态 | 主要位置 |
|---|---:|---|
| B站 crawler 注册 | 已支持 | `main.py` |
| 关键词搜索 | 已支持 | `media_platform/bilibili/core.py` |
| 指定 BV / URL 详情 | 已支持 | `media_platform/bilibili/core.py` |
| UP 主视频列表 | 已支持 | `media_platform/bilibili/core.py` |
| 评论抓取 | 已支持 | `media_platform/bilibili/client.py` |
| 播放地址获取 | 已支持基础版 | `get_video_play_url()` |
| 视频文件保存 | 已支持基础版 | `store/bilibili/bilibilli_store_media.py` |
| 字幕抓取 | 缺少 | 待新增 |
| DASH 音频下载 | 缺少 | 待扩展 |
| ASR 转写 | 缺少 | 待新增 |
| LLM 分析 | 缺少 | 待新增 |
| Trove 导出 | 缺少 | 待新增 |

当前下载逻辑主要处理 `durl`：

```python
durl_list = result.get("durl")
```

但 B站大量视频会返回 `dash` 音视频分离流。后续 ASR 需要优先使用 `dash.audio`，而不是下载完整视频。

## 四、实施顺序

## 阶段 1：增加 B站字幕抓取

### 4.1 目标

优先获取 B站已有字幕，避免不必要的音频下载和 ASR 成本。

字幕优先级：

1. 官方 / UP 主字幕
2. 自动生成字幕
3. 无字幕时再进入 ASR

### 4.2 修改文件

主要修改：

```text
media_platform/bilibili/client.py
analysis/subtitle.py
analysis/bili_video_analyzer.py
```

可选修改：

```text
config/bilibili_config.py
```

### 4.3 Client 新增接口

在 `BilibiliClient` 中新增 player info 接口：

```python
async def get_player_info(self, aid: int, cid: int) -> Dict:
    uri = "/x/player/wbi/v2"
    params = {
        "aid": aid,
        "cid": cid,
    }
    return await self.get(uri, params, enable_params_sign=True)
```

新增字幕下载接口：

```python
async def get_subtitle(self, subtitle_url: str) -> Dict:
    if subtitle_url.startswith("//"):
        subtitle_url = f"https:{subtitle_url}"
    async with httpx.AsyncClient(proxy=self.proxy, follow_redirects=True) as client:
        response = await client.get(subtitle_url, timeout=self.timeout, headers=self.headers)
        response.raise_for_status()
        return response.json()
```

### 4.4 字幕解析逻辑

新增 `analysis/subtitle.py`，负责把 B站字幕 JSON 转为纯文本和结构化片段。

B站字幕常见结构：

```json
{
  "body": [
    {
      "from": 0.0,
      "to": 2.5,
      "content": "字幕内容"
    }
  ]
}
```

建议输出：

```json
{
  "source": "subtitle",
  "language": "zh-CN",
  "segments": [
    {
      "start": 0.0,
      "end": 2.5,
      "text": "字幕内容"
    }
  ],
  "text": "完整转写文本"
}
```

### 4.5 配置项

在 `config/bilibili_config.py` 增加：

```python
BILI_ENABLE_SUBTITLE = True
BILI_SUBTITLE_LANG_PRIORITY = ["zh-CN", "zh-Hans", "ai-zh", "en-US"]
```

### 4.6 验收标准

- 输入一个带字幕的 BV 号，可以生成：

```text
data/bili/videos/{aid}/subtitle.json
data/bili/videos/{aid}/transcript.txt
```

- `transcript.txt` 内容来自字幕，不触发 ASR。
- 字幕接口失败时不影响原有 B站详情和评论抓取。

## 阶段 2：补 DASH 音频下载

### 5.1 目标

为无字幕视频准备音频文件，供后续 ASR 使用。

当前 `get_bilibili_video()` 只选 `durl`，需要扩展为：

1. 优先选 `dash.audio`
2. 没有 `dash.audio` 再 fallback 到 `durl`
3. ASR 场景优先下载音频，不默认下载完整视频

### 5.2 修改文件

```text
media_platform/bilibili/client.py
media_platform/bilibili/core.py
store/bilibili/bilibilli_store_media.py
config/bilibili_config.py
```

### 5.3 播放地址参数调整

建议把 `fnval` 调整为支持 DASH：

```python
params = {
    "avid": aid,
    "cid": cid,
    "qn": qn_value,
    "fourk": 1,
    "fnval": 16,
    "platform": "pc",
}
```

### 5.4 音频选择逻辑

建议封装函数：

```python
def pick_best_dash_audio(play_url: Dict) -> Dict | None:
    dash = play_url.get("dash") or {}
    audio_list = dash.get("audio") or []
    if not audio_list:
        return None
    return max(audio_list, key=lambda item: item.get("bandwidth", 0))
```

取 URL 时兼容不同字段名：

```python
audio_url = (
    best_audio.get("baseUrl")
    or best_audio.get("base_url")
    or best_audio.get("backupUrl", [None])[0]
    or best_audio.get("backup_url", [None])[0]
)
```

### 5.5 媒体保存扩展

`BilibiliVideo` 当前只提供 `store_video()` / `save_video()`，可以新增通用保存方法：

```python
async def save_media(self, aid: int, content: bytes, file_name: str):
    pathlib.Path(self.video_store_path + "/" + str(aid)).mkdir(parents=True, exist_ok=True)
    save_file_name = self.make_save_file_name(str(aid), file_name)
    async with aiofiles.open(save_file_name, "wb") as f:
        await f.write(content)
```

文件命名：

```text
data/bili/videos/{aid}/audio.m4s
```

### 5.6 配置项

```python
BILI_ENABLE_AUDIO_DOWNLOAD = True
BILI_MEDIA_DOWNLOAD_MODE = "audio"  # audio | video | both
BILI_AUDIO_FILE_NAME = "audio.m4s"
```

### 5.7 验收标准

- 对返回 `dash.audio` 的视频，可以保存 `audio.m4s`。
- 对只返回 `durl` 的视频，仍能 fallback 到原有下载逻辑。
- 原有 `ENABLE_GET_MEIDAS` 行为保持兼容。

## 阶段 3：接入 ASR 转写

### 6.1 目标

当视频没有可用字幕时，使用音频生成 transcript。

### 6.2 路线选择

| 路线 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| OpenAI-compatible Whisper API | 快速 MVP | 准确、省开发量 | 需要 API key 和费用 |
| faster-whisper 本地转写 | 数据不出本地 | 成本可控 | 需要模型、显存或 CPU 时间 |

建议 MVP 先抽象 ASR 接口，不把具体供应商写死。

### 6.3 新增文件

```text
analysis/asr.py
```

建议接口：

```python
class ASRProvider:
    async def transcribe(self, audio_path: str) -> dict:
        raise NotImplementedError
```

输出结构：

```json
{
  "source": "asr",
  "provider": "openai-compatible",
  "language": "zh",
  "segments": [
    {
      "start": 0.0,
      "end": 3.2,
      "text": "转写内容"
    }
  ],
  "text": "完整转写文本"
}
```

### 6.4 ffmpeg 处理

ASR 前建议统一音频格式：

```text
audio.m4s → audio.wav
```

Windows 环境需要确认：

```powershell
ffmpeg -version
```

如果未安装，方案二选一：

- 文档提示用户安装系统 ffmpeg。
- 在项目 `tools/ffmpeg/` 放置固定版本，并通过配置指定路径。

### 6.5 配置项

```python
BILI_ENABLE_ASR = True
BILI_ASR_PROVIDER = "openai"  # openai | faster_whisper
BILI_ASR_MAX_DURATION_SECONDS = 1800
BILI_ASR_OUTPUT_FORMAT = "txt"
```

### 6.6 长视频策略

超过 `BILI_ASR_MAX_DURATION_SECONDS` 时：

- 有字幕：只使用字幕。
- 无字幕：跳过 ASR，输出提示状态。
- 后续可扩展为分段转写。

### 6.7 验收标准

- 无字幕视频可生成 `transcript.txt`。
- ASR 输出带 `source=asr`。
- 未配置 API key / 未安装 ffmpeg 时，错误信息清晰，不影响基础采集。

## 阶段 5：接入 LLM 摘要和标签

### 8.1 目标

基于标题、简介、统计、评论和 transcript 生成结构化分析结果。

### 8.2 新增文件

```text
analysis/llm.py
```

### 8.3 输入内容

LLM 输入建议包含：

```text
标题
简介
UP主
发布时间
播放 / 点赞 / 投币 / 收藏 / 评论数
字幕或 ASR 转写文本
热评
```

### 8.4 输出结构

```json
{
  "summary": "视频摘要",
  "key_points": ["要点1", "要点2"],
  "tags": ["标签1", "标签2"],
  "content_type": "教程/观点/测评/剧情/新闻/其他",
  "sentiment": "正向/中性/负向",
  "audience": "目标受众",
  "action_items": ["可执行建议"],
  "risk_flags": ["争议点/广告/不确定信息"]
}
```

### 8.5 Provider 抽象

建议兼容 OpenAI-compatible API：

```python
class LLMProvider:
    async def analyze_video(self, payload: dict) -> dict:
        raise NotImplementedError
```

配置项：

```python
BILI_ENABLE_LLM_ANALYSIS = True
LLM_BASE_URL = ""
LLM_API_KEY = ""
LLM_MODEL = "deepseek-chat"
BILI_LLM_MAX_TRANSCRIPT_CHARS = 30000
```

### 8.6 长文本处理

超过 `BILI_LLM_MAX_TRANSCRIPT_CHARS` 时：

1. 按段落 / 时间戳切块。
2. 先做分块摘要。
3. 再做总摘要。

MVP 可以先截断，并在 JSON 中记录：

```json
{
  "transcript_truncated": true,
  "transcript_chars_used": 30000
}
```

### 8.7 验收标准

- `analysis.json` 中有 `summary`、`key_points`、`tags`。
- Markdown 中同步写入摘要和关键点。
- LLM 请求失败时保留 transcript 和基础分析文件。

## 五、MVP 里程碑

### MVP 1：字幕版分析

目标：输入 BV 号，生成包含元数据和字幕全文的 Markdown / JSON。

范围：

- 新增字幕接口
- 字幕解析
- `tools/analyze_bilibili_video.py`
- JSON / Markdown 输出

不包含：

- ASR
- LLM
- Trove API
- WebGUI

验收命令：

```powershell
uv run python tools/analyze_bilibili_video.py --id "BVxxxx" --output markdown,json
```

产物：

```text
data/bili/videos/{aid}/subtitle.json
data/bili/videos/{aid}/transcript.txt
data/bili/analysis/{aid}.json
data/bili/analysis/{aid}.md
```

### MVP 2：无字幕视频 ASR

目标：无字幕视频也能生成 transcript。

范围：

- DASH 音频下载
- ffmpeg 音频转换
- ASR Provider
- transcript fallback

验收命令：

```powershell
uv run python tools/analyze_bilibili_video.py --id "BVxxxx" --with-asr
```

### MVP 3：LLM 摘要

目标：生成摘要、关键点、标签、风险提示。

范围：

- LLM Provider
- 结构化 JSON 输出
- Markdown 摘要区写入

验收命令：

```powershell
uv run python tools/analyze_bilibili_video.py --id "BVxxxx" --with-llm
```

### MVP 4：Trove 导出

目标：生成 Trove 友好的 Markdown，必要时推送 API。

范围：

- Markdown front matter
- Trove field mapping
- 可选 API exporter

## 八、风险与控制

### 8.1 平台规则与用途

项目声明仅供学习和研究，扩展时必须继续控制：

- 请求频率
- 下载数量
- 并发数
- 数据用途
- 登录态使用范围

### 8.2 DASH 与登录态

B站部分视频、高清资源、字幕接口可能依赖登录态。当前项目已有：

- qrcode 登录
- cookie 登录
- CDP 模式

扩展应优先复用现有登录能力。

### 8.3 ffmpeg 依赖

ASR 很可能需要音频转换。Windows 上必须明确 ffmpeg 安装方式，否则用户会在 ASR 阶段失败。

### 8.4 长视频成本

建议默认限制 30 分钟：

```python
BILI_ASR_MAX_DURATION_SECONDS = 1800
```

超过限制时不自动 ASR，避免耗时、OOM 或费用失控。

### 8.5 LLM 成本与隐私

LLM 分析可能把 transcript 发给第三方 API。需要：

- 默认关闭 LLM
- 配置中显式启用
- 文档中说明数据会发送到配置的 API
- 记录输入截断策略

## 九、最终推荐路线

按优先级执行：

1. 先做字幕抓取，最快得到 transcript。
2. 再补 DASH 音频下载，覆盖无字幕视频。
3. 接入 ASR，形成完整文本来源 fallback。
4. 生成 Markdown / JSON 分析文件，先不碰数据库。
5. 接 LLM 摘要和标签，兼容 OpenAI-compatible API。
6. 再做 Trove 导出器，Markdown 优先，API 其次。
7. 最后再集成 WebGUI。

这条路线能最大化复用 AiWorker 现有 B站采集能力，同时把风险控制在新增的 `analysis` 模块内。第一阶段完成后，即使没有 ASR 和 LLM，也已经能产出可导入知识库的 B站视频文本资料。

# AiWorker 本机管理能力扩展方案

## 1. 目标与边界

在不引入 FEBS 的 Java/Shiro 技术栈、也不新增会话管理的前提下，为
AiWorker 的本机 WebGUI 补齐四项后台治理能力：

1. 组织/部门树、用户部门归属和项目成员角色。
2. 可筛选、可导出的管理审计中心。
3. 以现有权限目录为依据的可配置导航。
4. 基于现有 `JobManager` 的本机任务调度、重试、并发限制、执行记录和告警。

本方案只面向单机常驻的 WebGUI 进程。SQLite 继续作为系统配置和治理数据的
存储，不设计跨机器抢占、分布式锁、集群调度或外部消息队列。

## 2. 现状与原则

现有系统已具备用户、角色、权限、会话、项目成员、工作流和审计数据模型。
权限服务支持 `task`、`project`、`managed_projects`、`all` 四种数据范围；
`NavigationService` 负责根据有效权限显示静态导航；`JobManager` 负责启动、
监控、暂停、恢复、重试和持久化单次任务状态。

因此，本次扩展遵循以下原则：

- 权限唯一来源：继续使用 `identity` 的角色和权限体系，不复制一套菜单权限。
- 页面和 API 的授权独立于导航：导航只控制可见性，绝不作为访问控制手段。
- 项目角色与部门职务分离：`project_members` 只描述项目协作身份。
- 调度配置和执行记录可恢复：WebGUI 重启后恢复启用的计划，保留历史记录。
- 本机优先：避免为单机需求引入队列、服务注册、分布式锁或第二个后台服务。
- 敏感信息不进入审计或调度参数展示；沿用现有审计脱敏规则。

## 3. 方案对比与结论

### 方案 A：原生扩展现有 FastAPI 模块

新增组织、导航和调度服务，审计服务在现有基础上扩展查询导出；所有模块共享
当前系统数据库和权限服务。

优点：业务边界清晰，无双账号和双权限问题，能直接复用现有模板、路由、审计和
`JobManager`。缺点：需要补齐管理界面与迁移测试。

### 方案 B：独立部署传统后台系统

将 FEBS 或同类后台作为旁路系统，另行维护用户、角色、菜单与日志。

优点：传统后台页面较完整。缺点：身份、权限、项目成员和审计会分裂，且 FEBS 的
依赖栈陈旧，与当前 FastAPI 应用不兼容。

### 方案 C：只增加管理页面

在现有页面上临时展示部门、审计和任务信息，但不建立持久化模型和服务接口。

优点：初期工作量最小。缺点：组织关系、调度定义和执行历史无法可靠恢复，也无法
形成可测试的业务边界。

结论：采用方案 A。

## 4. 总体架构

```text
WebGUI 生命周期
  ├─ IdentityRepository / PermissionService
  │    ├─ 部门与用户归属
  │    ├─ 项目成员角色
  │    └─ 可配置导航项
  ├─ AuditService
  │    └─ 查询、导出、操作留痕
  └─ LocalScheduleService
       ├─ APScheduler BackgroundScheduler
       ├─ schedule_definitions / schedule_runs
       └─ JobManager.create_job()
            └─ Worker 进程、事件、产物、单次任务状态
```

`IdentityRepository` 继续是用户、角色、权限、部门和导航配置的主存储入口。
`AuditService` 继续写入统一的 `audit_logs`。调度模块只创建和跟踪任务，不复制
`JobManager` 的进程监控、任务文件、事件和产物逻辑。

## 5. 组织与项目成员

### 5.1 数据模型

新增 `departments`：

| 字段 | 含义 |
| --- | --- |
| `id` | UUID 主键 |
| `name` | 同一父部门下唯一的部门名称 |
| `parent_id` | 父部门，可为空表示根部门 |
| `sort_order` | 同级显示顺序 |
| `status` | `active` 或 `disabled` |
| `created_at` / `updated_at` | 审计与排序辅助时间 |

新增 `user_departments`：

| 字段 | 含义 |
| --- | --- |
| `user_id` | 现有用户 |
| `department_id` | 部门 |
| `is_primary` | 是否主部门；每个用户最多一个主部门 |
| `created_at` | 归属建立时间 |

保留现有 `project_members(project_id, user_id, project_role, status, ...)`。
它表示某用户在某项目中的协作身份，例如负责人、策划或编剧；部门不自动授予
项目访问权，也不改变既有数据范围判定。

### 5.2 服务与规则

新增 `DepartmentService`，负责创建、改名、移动、停用、列树、维护用户归属。

- 移动部门前验证目标父节点不是当前节点或其后代，避免树形成环。
- 非空部门不能直接删除；先迁移子部门和用户归属，或将其停用。
- 被停用部门不允许新增归属，但保留历史归属数据。
- 一个用户可属于多个部门；主部门只能有一个，设置新主部门时在同一事务内取消旧值。
- 部门及用户归属的新增、修改、停用均写入 `audit_logs`。

### 5.3 管理界面

系统管理新增“组织架构”页面：左侧为树，右侧为部门详情和成员列表。用户管理页
提供部门归属编辑；项目成员页继续只编辑项目角色，不混入部门字段。

所需权限以新权限码表达，例如 `department.read`、`department.manage`。页面路由和
API 分别声明所需权限，导航仅据此显示入口。

## 6. 管理审计中心

### 6.1 查询能力

复用 `audit_logs` 及 `AuditService.query()`，扩展下列组合筛选条件：

- 操作人：用户 ID、用户名或显示名。
- 项目：项目 ID。
- 动作：精确动作或动作前缀，例如 `workflow.*`、`schedule.*`。
- 结果：`success`、`failure`。
- 时间：开始时间（含）与结束时间（不含）。
- 目标：资源类型、资源 ID，用于排查单个任务或部门变更。

查询结果按 `created_at DESC, id DESC` 排序，并限制单次返回量；前端使用明确的页码
和每页条数，避免一次性加载完整审计库。

### 6.2 导出能力

提供 CSV 与 XLSX 两种导出：

- CSV 使用 UTF-8 with BOM，保证 Excel 打开中文不乱码。
- XLSX 使用项目既有 `openpyxl` 依赖。
- 导出沿用审计数据中已脱敏的摘要字段，不额外读取密码、token、cookie、密钥或
  原始请求体。
- 导出文件名包含筛选时间范围和生成时间；导出操作本身记录为 `audit.export`。
- 仅拥有 `audit.read` 的系统管理员可查看和导出全量审计；项目负责人只可查看其
  管理项目的记录，并且不能导出超出项目范围的数据。

### 6.3 管理界面

“审计日志”页提供固定筛选栏、结果表格、详情侧栏和导出按钮。详情仅展示脱敏后的
变更前后摘要、请求 ID、IP、用户代理、操作原因与结果，不渲染原始 JSON 为 HTML。

## 7. 可配置导航

### 7.1 数据模型

新增 `navigation_items`：

| 字段 | 含义 |
| --- | --- |
| `id` | UUID 主键 |
| `parent_id` | 父导航项，可为空 |
| `label` | 显示名称 |
| `icon` | Bootstrap Icon 名称 |
| `route` | 站内页面路由 |
| `required_permission` | 可见导航所需的现有权限码 |
| `sort_order` | 同级顺序 |
| `is_enabled` | 是否显示 |
| `is_system` | 内置导航，禁止删除 |

初始迁移将 `NAVIGATION_CATALOG` 的栏目和子项导入该表，保证当前导航顺序和入口不变。

### 7.2 授权边界

`NavigationService.items_for()` 从启用的配置中构建可见项，依据
`required_permission` 与 `Principal.permissions` 过滤。导航项没有权限定义权：

- 路由页面继续由 `require_page()` 保护。
- API 继续由路由依赖或明确的权限检查保护。
- 新导航项的 `required_permission` 必须是权限目录中已登记的权限码。
- 配置一个没有对应页面路由的入口时，保存失败；删除或停用导航项不会撤销页面访问。

这样可避免“知道 URL 就绕过菜单”的传统后台授权问题。

### 7.3 管理界面

系统管理新增“导航配置”页，支持排序、启停、编辑标签和图标。内置项的路由和所需
权限不可由页面修改；新增自定义入口仅允许指向已登记的内部页面。每次变更写入审计。

## 8. 本机任务调度

### 8.1 调度模型

新增 `schedule_definitions`：

| 字段 | 含义 |
| --- | --- |
| `id` | UUID 主键 |
| `name` | 本机唯一计划名称 |
| `job_type` | 白名单任务类型 |
| `payload_json` | 经校验的任务参数 |
| `trigger_type` | `cron` 或单次 `date` |
| `trigger_config_json` | cron 字段或执行时间 |
| `timezone` | 固定为 `Asia/Shanghai` |
| `is_enabled` | 是否参与调度 |
| `max_retries` | 失败后最多重试次数，默认 3 |
| `misfire_policy` | 默认 `skip`，错过时间不补跑 |
| `created_by` / `updated_by` | 配置责任人 |

新增 `schedule_runs`：

| 字段 | 含义 |
| --- | --- |
| `id` | UUID 主键 |
| `schedule_id` | 对应计划 |
| `job_id` | `JobManager` 创建的任务 ID |
| `attempt` | 首次执行为 1，重试递增 |
| `status` | `queued`、`running`、`succeeded`、`failed`、`skipped`、`cancelled` |
| `scheduled_at` / `started_at` / `finished_at` | 触发与执行时间 |
| `error_summary` | 截断且脱敏后的失败摘要 |
| `retry_of_run_id` | 上一次尝试，首次为空 |

### 8.2 运行机制

WebGUI 生命周期创建 `LocalScheduleService` 并启动 APScheduler 的
`BackgroundScheduler`。应用启动时从 `schedule_definitions` 读取已启用计划并注册
触发器；关闭时停止调度器，不主动终止已经交给 `JobManager` 的任务。

调度器仅接受明确白名单中的任务类型：爬取、榜单更新、素材下载及其已有分析任务。
`payload_json` 通过对应的 Pydantic 请求模型校验后才能保存或启动。计划触发时执行：

1. 创建 `schedule_runs` 记录。
2. 检查同一计划是否已有 `queued` 或 `running` 记录；存在则本次记为 `skipped`。
3. 调用 `JobManager.create_job()`，并在任务 `extra` 中写入 `schedule_id` 和
   `schedule_run_id`。
4. 监听或轮询对应 `job_id` 的终态，将 `JobManager` 的结果回写到 `schedule_runs`。
5. 失败且未超过重试次数时，分别在 1、5、15 分钟后建立一次性重试触发器。

现有 `JobManager` 的平台冲突检查仍是执行层最后一道并发保护；调度层额外保证同一
计划不重入。调度计划的新增、修改、停用、手动运行、重试、取消和失败均写入审计。

### 8.3 告警与管理界面

本机告警不接入邮件、短信或第三方 Webhook。系统后台提供“调度中心”页面，展示：

- 启用状态、下次执行时间、最近执行结果和连续失败次数。
- 运行中/失败计划的数量徽标。
- 失败记录的错误摘要和关联 `job_id`，可跳转既有任务详情与日志。
- 手动运行、暂停计划、恢复计划和立即重试按钮。

失败告警通过管理页醒目状态、系统日志和审计记录形成闭环；连续失败达到三次时，
计划自动暂停，等待管理员处理，避免持续消耗本机资源。

每一阶段完成后均运行对应单元测试和 WebGUI 路由集成测试；完成四阶段后执行完整
`pytest` 与 `pre-commit run --all-files`。

## 10. 验收标准

- 管理员可维护多层部门、用户多部门归属和唯一主部门；非法移动和非空删除被拒绝。
- 项目成员角色与部门归属互不影响，既有工作流授权测试保持通过。
- 审计中心能按用户、项目、动作、结果和时间组合筛选，并导出脱敏的 CSV/XLSX。
- 菜单只向具备所需权限的用户显示；直接访问页面/API 仍由独立权限检查拒绝越权。
- WebGUI 重启后已启用计划恢复；每次运行都能关联到 `JobManager` 的 `job_id`。
- 同一计划不会并发重入；失败按 1/5/15 分钟最多重试三次，连续失败三次后自动暂停。
- 调度、组织、导航和审计导出操作均有可检索审计记录。
