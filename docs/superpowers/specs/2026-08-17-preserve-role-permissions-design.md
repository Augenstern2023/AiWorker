# 保留后台角色权限配置设计

## 背景

AiWorker 在 WebGUI 启动时调用 `IdentityRepository.seed_defaults()`。当前实现会删除所有内置角色的现有权限，再按代码中的默认角色目录重新写入。管理员通过后台对内置角色进行的授权、撤权或数据范围调整，因此会在服务重启后丢失。

本次变更要求所有内置角色的后台权限配置永久保留。内置角色包括选品运营、创意策划、编剧、项目负责人和系统管理员。

## 目标行为

1. 内置角色首次创建时，写入代码定义的默认权限及数据范围。
2. 内置角色已经存在时，启动初始化不得新增、删除或修改其角色权限。
3. 管理员在后台新增权限、移除权限或调整数据范围后，重复初始化及服务重启均保留该配置。
4. 权限目录、权限中文名称和权限依赖关系仍由代码维护，并在启动时同步。
5. 内置角色名称、说明和系统角色标志继续随代码目录更新。
6. 自定义角色、用户与角色绑定、角色页面授权保持现有保留行为。

## 方案

修改 `IdentityRepository.seed_defaults()` 的内置角色初始化分支：

- 查询角色代码是否已经存在。
- 继续以 upsert 方式同步角色元数据。
- 仅当角色在本次初始化前不存在时，写入该角色的默认权限闭包。
- 对已经存在的角色完全跳过角色权限删除和默认权限插入。
- 保留权限目录和权限依赖关系的现有精确同步逻辑。

角色页面授权当前已经采用“仅首次创建时写入默认值”的规则，本次让角色权限采用相同生命周期。

## 数据流

首次部署：

`启动初始化 -> 创建内置角色 -> 写入默认权限 -> 写入默认页面授权`

后续启动：

`启动初始化 -> 同步权限目录/依赖和角色元数据 -> 保留现有角色权限及页面授权`

后台配置：

`管理员修改角色权限 -> 数据库存储 -> 后续启动不触碰该角色权限`

## 兼容性边界

代码以后新增某项默认角色权限时，已有部署不会自动获得该权限。管理员需要通过后台显式授权，或者由针对该业务变化的数据库迁移完成授权。这是确保后台撤权不会被启动过程反向覆盖的必要边界。

权限目录中被正式废弃并由现有初始化逻辑显式清理的权限，仍可从目录和依赖表移除；数据库外键级联可以清理由该权限产生的角色授权。该机制不用于重置仍然有效的权限。

## 测试策略

1. 验证空数据库首次初始化后，全部内置角色仍获得默认权限。
2. 修改一个已有内置角色的权限集合及数据范围，再次初始化，断言配置完全不变。
3. 验证重复初始化仍同步权限依赖目录，但不清除内置角色后台配置。
4. 验证自定义角色和用户角色绑定保持不变。
5. 运行身份权限相关测试和 PostgreSQL 集成测试，确认生产数据库实现行为一致。

## 非目标

- 不改变选题库的数据过滤规则。
- 不自动给编剧添加 `topic.read`；永久保留机制上线后，该权限由后台配置决定。
- 不修改角色页面授权模型。
- 不引入权限配置版本系统或新的管理接口。
